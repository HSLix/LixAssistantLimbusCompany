# 验证与试运行

1. 工具成功不等于完整 Validate 通过。修改 Candidate 后调用 validate_and_publish 完整校验并保存不可变版本，按实际错误继续修正；校验失败仍可修改。Validator 会导入 Python，不是安全沙箱；校验通过不等于真实游戏验证通过。
2. 新修改运行前必须先 Publish 为不可变版本，不执行可变 Candidate。Developer 用明确 Manifest ID 的 trial_run；Runtime 用 validate_and_publish(summary="修复问题简述") 写入 AdditionalMessage，再 recheck(manifest_id) 结束本轮并交还 Runtime，仅重调当前失败入口。Publish 本身不执行、不设置 Default，不存在额外永久批准流程。
3. Developer trial_run 的 use_saved_config 默认 true，采用已保存页面配置及启用任务次数；设为 false 才使用显式 run_state（task_repetitions、settings），省略为空。inputs 只承载普通 Component 参数，Plan 无业务入口参数。试运行失败交回当前 Developer Session，不启动 Runtime Agent。
4. 按改动范围验证，不要求每次完整游戏实跑：返回契约核对调用方及输出，分派／预算检查对应分支、无效计数及超限出口，识别试验核对命中与误识别。可用无游戏输入的局部检查时先利用；替身检查不等于游戏验收。完整路径仅按用户要求或变更需要运行；仅分析、查看资料不强制修改或发布。
5. 大部分现场只有一次低成本试运行机会：操作可能不可逆，再次验证需重置副本重新推进或人工协助，成本很高。运行前明确起点、要验证的变化、终点／输出及应保留的证据，根据当前画面确认起点；不为强行多次试跑擅自结束探索、消耗资源或要求人工复位。确需复位时先明确后果并依据已有授权，缺必要授权再请求；这不是绝对只准运行一次。
6. 高试运行成本不是堆砌状态检测的理由。优先复用现有 Asset，选择标题、特色按钮等少量易识别且较少误判的特征，允许根据新现场逐步改善；不能凭共有导航标志判断起点就绪。试运行期间等待工具结果，不并行修改或操作游戏。
7. 启动拒绝没有 Run ID，不能当作已运行。结束后利用实际日志与截图对照起点、变化和输出；已在终点零动作返回只证明该入口行为，不能替代完整路径验证；恢复后成功也不证明原路径顺利完成。先分析已保留证据，不无依据反复重试；用户停止后总结并等待新指示。
8. 总结实际修改、静态校验、已发布版本、真实运行和仍待确认的适用情景；区分只读识别试验、替身测试和游戏输入路径。TODO 不等于保护已实现，单页／同图命中不等于跨场景稳定。按常驻最终 JSON 契约判定 revise_success，用户明确要求成功试运行时，未运行或失败不能报告修订任务已完成。

## 首次观察后补齐退出信号

- 退出信号可依据新特征出现或原状态可靠特征消失，不要求先看到新页面才能设计。开发时仍无法确定退出依据，允许先实现可靠的入口条件、一次预期动作及有限等待，注明退出信号待观察；按前述规则校验发布后，仅独立试运行这个 Step 一次来获取落点，不将未补齐的步骤接入自动循环反复输入。未确认目标时返回 completed=false 并说明原因，不能临时无条件返回完成。
- 对照动作日志及运行前后截图，确认实际执行情况、画面变化与下一状态。变化本身不证明局部目标达成：先判断是否是预期目标、正常过渡或异常画面；必要时等待过渡或请求人工商讨。依据新现场选取退出特征，不凭猜测提前造信号，也不因需要补齐就堆叠大量检测。
- 补齐后让 Step 每次先重新截图并检测退出／完成信号；证据满足局部目标则返回 completed=true，若只足以停止原动作而未证明目标达成则交回未达成，均不重放原动作。未命中再检查入口，入口也不适用则交回。校验发布新版本后，可保留当前落点，再独立运行同一 Step，核对它是否由退出分支零输入返回及结果是否符合职责，避免重置副本重走原路径。采用消失信号时确认其适用范围，不能将识别错误或短暂遮挡视作完成；必要时先用只观察识别试验确认候选，不能为验证退出而盲目重放动作。
- 分别报告第一次的动作／落点证据和第二次的完成态重入证据。后者仅验证当前目标画面的退出识别与不重复输入，不能声称完整路径或其他场景已通过；若当前现场已经变化，则按新现场决定能验证什么，不强行恢复进度。
