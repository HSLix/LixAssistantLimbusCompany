# 循环分派与正常过渡等待

用于编写或修订 Task Workflow／Subworkflow 的统一分派，不是执行器自动提供的能力；按实际 Component 签名实现，不能假设已有共用等待 Step。新约定按需迁移，不改写历史发布版本。

默认由 Workflow 直接调用 observe 动作，在同一轮截图上判断多个条件并分派，可复用同帧局部 OCR 结果。只有多个 Workflow 确实复用同一套场景分类，或需要独立验证该识别能力时，再考虑提取识别 Step；临时识别试验不要求永久保留分类层。动作 Step 的局部适用性及完成检查仍保留，无需重复识别全部场景。

Workflow、Step 和 Recovery Rule 内的状态轮询都要及时刷新截图：匹配／OCR 与 observe.wait 不会自动更新内存帧，不能只在循环外截图一次。循环内完成动作、等待或子流程调用后，若还需判断状态，先重新截图并重算识别结果，或直接 continue 回到会截图的顶部。不要假设子流程留下的帧一定是返回时的新状态；也不能刷新截图后仍使用旧的 OCR 文本、匹配列表或场景变量。纯观察、无动作／等待的同轮多个条件仍可共享一帧。

## 一轮分派

1. 重新截图，先确认是否有 Connecting／Combat Tips／Now Loading 等可靠的正常过渡特征；命中时调用共用等待 Step，再重新观察和完整分派。
2. 没有正常过渡时，根据新画面选择一个适用业务分支。完成后回到顶部，不沿用动作前截图检查后半段分支。分支条件有重叠时按可靠特征及业务优先级收窄，不仅调整代码顺序掩盖误识别。
3. 可交回动作 Step 的最小结果为 `{"completed": true/false, "reason": "说明"}`。记录原结果；完成才清零业务连续无效计数，未达成不继续执行依赖其成功的动作。调用方不需逐种解析 reason。
4. 未达成结果先留到下一次新观察：若有已确认正常过渡，先等待；没有过渡或过渡结束后再统一结算这一次未达成，不重复累计。等待本身不计无效，也不清零既有无效计数；等待超限按下节处理。
5. 未命中分支也计一次无效。连续无效初始上限为 3 次，未耗尽时 `ctx.action("observe.wait", seconds=1.0)` 后重新观察；达到上限抛 ExecutionFailure，不再开启一次尝试。已知页面或过渡提示消失本身都不是局部目标达成。
6. 单次任务的完成必须有任务级证据，不把子 Step 正常返回或出现新页面直接当作整场完成。局部交回可包含确有需要的业务数据；流程汇总依实际契约处理。

## 各层预算

- Workflow 用有界 for，每轮包括无效分派和过渡处理都受自身总轮数限制，总计数不随局部成功清零。耗尽后主动抛失败，说明未能完成的目标与最后观察；这不是正常完成。
- 可能很长的单次 Task，在源码设稍大且足以覆盖正常执行的固定总循环上限，作为连续无效计数未发挥作用时的兜底；实际证据表明不足再增加。Skill 不指定统一数值，不为这一常量扩展 RunState 或页面配置。短 Subworkflow 按各自职责设置总上限。
- 上限是每次调用的循环次数，不是共享剩余次数或绝对秒数。截图、识别和子 Step 耗时另计；Step 内部循环也必须有界，不能依靠上层循环中断尚未返回的 Step。
- 这些是业务循环计数，不能修改框架只读 recovery_count。Step 正常返回（包括 completed=false）在执行器层仍属正常返回，会按原规则清零框架恢复计数；业务无效计数由 Workflow 独立维护。

## 共用正常过渡等待 Step

- 只在可靠特征确认的正常过渡上等待，不包含游戏控制输入，不解释业务目标是否完成。使用现有模板或按需局部 OCR，依据当前截图尺寸确定适用区域；读取失败不能当作提示消失。
- 初始最多观察 60 轮，轮间用 observe.wait 等待 1 秒，使用有界 for。截图与识别也耗时，不宣称严格 60 秒。可返回明确的消失／timeout 状态，不套用动作 Step 的 completed 含义。
- 预算内提示消失：交还 Workflow，重新截图和分派；不重复原动作，不据此报告业务完成或清零无效计数。
- 返回 timeout：Workflow 必须重新截图一次。过渡已消失则重新分派；仍存在则抛“正常过渡等待超限”，进入既有恢复流程，不立即重开相同等待预算。未知画面不是“仍在加载”，按普通未知分派处理。
- 这个截止边界不能消除之后网络自行恢复的时序窗口。恢复检测零匹配不意味着业务已完成，也不会自动证明需要再次输入；遵循现有执行器处理。
