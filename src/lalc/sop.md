# SOP

## 填写说明

此文件由开发者维护，不由 LALC Agent 编辑。下面三个 XML 标签内提供简单默认流程，可按使用反馈调整；空正文也不会阻止使用。
只将步骤写入对应正文，保留分级标题及标签，每组标签必须恰好一对，不能互相嵌套，也不要在示例中重复它们。
填写说明和标签外的文字不会发送给模型。

- Construct：构建、扩展和修复 Workflow 的默认流程。
- Repair：分析故障、定位原因和修复 Workflow / Asset 的默认流程。
- Asset：两种模式共用的素材处理流程。
- 正文可使用 Markdown 编号、判断条件、异常分支和结束条件；按实际任务取舍，不要求无关任务执行所有步骤。
- 工具定义说明能做什么，SOP 说明何时、如何组合使用；不复制完整参数 Schema，不写未启用工具的授权承诺。
- 区分静态 Validate、保存不可变版本的 Publish、显式版本试运行及真实游戏验证；不得将前两项当作游戏验收通过。
- 图片流程必须遵守预览后按同一 preview_id 保存的契约；不要用流程指导覆盖 Core 安全规则。
- 每条用户消息执行开始时重新读取；Construct 只加载 Construct + Asset，Repair 只加载 Repair + Asset，执行期间文件变动到下一轮才生效。
- 源码运行编辑本文件；Windows ZIP 成品编辑程序目录下 `_internal/lalc/sop.md`。程序更新可能替换文件，请自行保留填写内容；没有用户数据目录副本或 GUI 编辑器。
- 文件缺失、标签缺失或重复会在模型请求前报错，请恢复正确结构；用 UTF-8 保存。

## Construct

<construct_sop>
1. 明确本轮目标和完成条件；先检查当前 Candidate，按需读取参考 Manifest、源码和动作契约，不猜测未提供的接口或游戏状态。
2. 信息足够时执行满足目标的最小修改，复用已有能力；关键信息不足时说明缺少什么，不编造实现依据。
3. 修改 Workflow 后执行完整 Validate；根据实际错误继续修正。仅分析或查看资料时，不要求修改、校验或发布。
4. 按用户要求和验证需要决定是否试运行；运行新修改前先 Publish，再显式指定保存的 Manifest ID。等待实际结果，必要时查看 Run 日志，不把启动拒绝当作已运行。
5. 总结完成内容、校验和试运行结果、未验证事项或阻碍，按最终 JSON 契约回答，不夸大完成程度。
</construct_sop>

## Repair

<repair_sop>
1. 根据用户描述、已有日志和当前 Candidate 确认故障；需要现场证据时再截图，不根据旧截图猜测当前状态。
2. 读取相关源码和动作契约，定位有证据支持的原因；证据不足时明确缺少的信息，避免无依据的大范围改写。
3. 对原因做最小修复；修改 Workflow 后执行完整 Validate，根据错误继续修正。素材问题按共用 Asset 流程处理；仅分析时不强制修改。
4. 按用户要求和验证需要决定是否试运行；新修改必须先 Publish，再用明确 Manifest ID 运行并检查实际结果。失败时根据日志继续定位，避免不改变依据地反复重试；用户停止后总结并等待指示。
5. 分别说明已修改、静态校验、实际运行及仍未确认的部分，按最终 JSON 契约报告；校验通过不等于游戏故障已修复。
</repair_sop>

## Asset

<asset_sop>
1. 先确认素材逻辑名、用途及已有图片；仅在确有需要时新增或归档移除，注意共享素材变更会影响其他 Session。
2. 需要确定现场区域时获取当前截图，结合原图、坐标网格及同图 OCR 定位。game_screenshot 附带完整 OCR 结果，坐标为客户区像素；ocr_error 表示识别失败，不是没有文字。OCR 不支持韩文，分数不证明识别正确。保存前调用 preview_crop，检查返回的区域标线图、干净裁剪图和同图匹配结果。
3. 预览符合目标后，用该次返回的 preview_id 调用 crop_asset 保存相同像素；区域不合适就重新预览，预览 ID 失效就重新获取，不使用猜测的 ID。同图匹配不代表跨状态可靠。
4. 需要时更新 Candidate 中的素材引用；若修改了 Workflow，执行完整 Validate。按需通过明确已发布版本试运行检查实际匹配，不用预览或校验结果替代游戏验证。
5. 归档移除前确认逻辑名、具体哈希和理由，仅使用 remove_asset；工具失败时先检查原因，不假定已移除。总结实际保存或移除的素材及尚未验证的适用状态。
</asset_sop>

## Page 

<page_sop>
1. **理解需求**：明确页面的新建或修改目标，检查已有页面、配置和相关 Plan，确认页面字段及业务用途；仅分析时无需创建草稿。
2. **检查兼容性**：保留稳定的 PAGE_ID / TASK_ID 和已有配置，检查字段变化及 Plan 的参数使用。若需要破坏兼容，先说明影响，并通过 request_feedback 获取明确授权；Skip 不构成授权。
3. **创建草稿**：通过 page_* 专用工具创建或修改当前 Session 的页面草稿。新增页面从空白开始，修改页面以已安装版本为基础；确保满足 PAGE_ID、PAGE_NAME、create_page(context) 和 QWidget.submit() 契约。
4. **独立预览**：调用 page_preview，提供简洁的修改说明供开发者审查。预览失败时根据工具错误修正草稿，必要时重新预览；不将加载成功视为配置兼容或业务验证通过。
5. **人工审批**：等待预览结果。installed 表示指定内容版本已安装；关闭或跳过不安装，可继续修改；取消轮次则停止当前任务。草稿改变后需要重新预览和审批。
6. **总结结果**：说明页面修改、兼容性影响、预览和安装状态，以及尚未验证的业务行为。安装后提醒开发者主动重载应用；预览中的试填配置不会被安装。
</page_sop>
