# 游戏版本与 Agent 历史关联：设计确认记录

2026-11-01。15 项决定及影响审查已由开发者整体回复“同意”确认，授权实施。实际完成及验证范围另见[实施记录](game-version-session-implementation.md)。

## 已确认

### 1. 每轮开始前观测

每轮用户提交消息、启动 Agent 处理前观测一次游戏版本；同一轮内部暂不重复探测。各轮保留独立观测记录，不覆盖历史记录；同一 Session 汇总各轮关联到的多个版本。仅打开或查看历史不因此产生新的轮次观测。

依据：开发者对选项 A 明确回复“同意 A”。

### 2. 版本组合与时间更新

版本按 `(game_version, steam_build_id)` 两字段组合分组，缺失字段保留缺失，不与字段完整的组合合并；两者都缺失时归入 Unknown。展示优先使用游戏内版本，并保留 Steam Build ID 区分组合；按游戏内版本筛选可覆盖多个组合。

每轮观测只更新本轮实际观测到的组合及其与当前 Session 关联的最近观测时间，不因当前 Session 继续活动而更新它关联的其他历史组合。每轮原始观测及其时间仍保留，不被最近时间汇总覆盖。

依据：开发者选择 A，并补充“观测时间的更新也是与两个字段组合分组更新，而且只更新最新的这组，历史对话的其他版本对应不更新”。

### 3. 所有现有 AI 日志入口纳入

GUI Construct / Repair、CLI Repair 及 Agent 连接测试 / 模型诊断日志均记录版本，保留来源类别以供检索区分。开发对话按每轮开始前观测；诊断在开始时观测一次。未来 Runtime 接入沿用版本记录规则，但本次不提前实现 Runtime。

依据：开发者对“全部纳入”选项 A 明确回复“A”。

### 4. 仅索引上线后新增观测

不扫描或导入旧历史，不修改旧日志，不反推历史版本。旧 Session 恢复并提交新消息时，仅记录新轮次的版本观测、建立关联；旧轮次不自动归入 Unknown，也不作为本次版本检索的已关联内容。

Unknown 用于新增观测中两个版本字段均获取失败的情况。每轮使用已知 Session UUID 增量更新索引，不通过遍历历史目录查找当前 Session 是否已索引。旧日志中未产生新观测的内容不出现在版本检索结果中。

依据：开发者明确回复“采用 B”。

### 5. 本次提供三个 Agent 历史工具

本次提供版本列表、按版本筛选 Session，以及按 Session UUID / 轮次分页读取 AI 历史内容三个工具。内容读取先返回文字，图片按需读取；复用既有日志引用展开、路径边界和哈希校验，不一次注入全部历史及图片。轮次保留版本标识，避免跨版本内容混淆。

现有 `read_run_log` 用于自动化运行 Trace，不以其替代 AI Session 内容读取。

依据：开发者对“本次实现三个工具”选项 A 明确回复“A”。

### 6. 版本筛选用于定位，不作为轮次读取限制

按版本找到 Session 后，默认读取匹配轮次，允许显式读取同一 Session 其他轮次。查看内容时，每轮均显示其版本组；不存在版本关联时显示 Unknown。此处 Unknown 也适用于上线前未观测的旧轮次，仅为读取时的展示，不将旧轮次补入版本索引或伪造观测时间。

其他版本轮次及未观测轮次不被归入筛选版本，图片读取同样保留所属轮次与版本组信息。

依据：开发者选择 A，并要求“每轮对话得能在查看的时候，看到属于的版本组，当然如果版本组不存在那就 Unknown”。

### 7. Steam 设置指向客户端根目录

User GUI 的 Steam 路径设置指向 Steam 客户端根目录，不将游戏所在库目录与客户端根目录混为一谈。程序读取该客户端 `steamapps/libraryfolders.vdf`，在各游戏库中查找 Limbus 安装清单并定位游戏文件，支持客户端与游戏位于不同磁盘。

保留路径缓存、缓存失效后重新发现、找不到时提示在 User GUI 设置路径的要求；自动发现顺序及多安装歧义处理见下文第 11 项。

依据：开发者对“设置 Steam 客户端根目录”选项 A 明确回复“A”。

### 8. 不要求游戏运行

游戏未运行时仍读取本地已安装版本，不启动、不激活游戏。观测表示本轮开始时磁盘上已安装客户端的版本信息，不证明游戏已登录、完成资源热更新或服务器状态与该版本一致。

依据：开发者对“照常读取本地安装文件”选项 A 明确回复“A”。

### 9. GUI 与 CLI 共用只读历史工具

GUI Construct、GUI Repair、CLI Repair 均开放三个历史工具，允许只读检索本数据目录内已索引的跨入口历史，不提供日志编辑权限。各入口都记录版本不自动替代其工具白名单；须在各入口显式接入新工具。未来 Runtime 实际接入仍留 Stage 6。

依据：开发者对“全部开放”选项 A 明确回复“A”。

### 10. 游戏版本解析采用受限兼容

正常完整解析成功时读取游戏版本；仅对已验证的引擎 / 对象布局允许当前样本尾部 4 字节的兼容差异，不将“剩余 4 字节”视为所有未来格式都安全的规则。其他解析异常记录错误，游戏版本留空，仍独立尝试 Steam Build ID，且不阻止其他功能或对话。

不回退到任意版本字符串搜索或固定字节偏移。实施时明确已验证布局及校验依据，解析器升级重新验证。

依据：开发者对“限制兼容例外”选项 A 明确回复“A”。

### 11. Steam 发现与歧义处理

先验证已保存路径；仍有效时继续使用，不因存在其他候选而切换。失效后按注册表、常见安装位置、各磁盘第一级目录的顺序重新发现，不递归扫描整盘。候选通过库配置及 Limbus 安装清单验证。

重新发现时若无法确定唯一有效 Steam 安装，不擅自选择第一个候选；记录歧义错误，本轮版本归 Unknown，并提示在 User GUI 设置 Steam 客户端路径。查找失败或歧义不阻止 Agent 对话。

依据：开发者对“不擅自选择”选项 A 明确回复“A”。

### 12. 本轮版本上下文持久追加

本轮观测信息自动加入已有 `runtime_context`，随该轮新增用户消息持久保存并在续聊时原样恢复；不回写旧消息、不把最新版本替换进全部历史，也不修改系统提示词。诊断仅留证，不因此调用模型。

保留版本组、观测时间及失败状态；版本表示安装状态，不自动判定历史经验有效性。持久追加旨在保留已有上下文前缀，不承诺模型服务零 cache miss。

依据：开发者选择 A，并强调持久保存、每轮关联和避免修改已有上下文导致缓存失效。

### 13. 日志观测为事实来源，独立索引用于检索

每轮日志保存原始版本观测；数据目录内独立文件保存检索索引。日常工具查询索引，不扫描历史目录；独立索引丢失或损坏时可从已保存的观测重建，没有观测的旧轮次不导入。

索引写入失败记录错误，不阻止对话；索引不成为唯一的版本关联证据。重建是异常恢复操作，不在每轮重复扫描历史。具体存储实现与并发 / 写入中断处理在影响审查及实施中明确。

依据：开发者对“每轮日志保存原始观测，独立文件保存检索索引”选项 A 明确回复“A”。

### 14. UnityPy 使用 automation 可选依赖组

UnityPy 加入现有 automation 可选依赖组，固定本次验证过的版本；Windows 成品构建通过既有全部 extras 安装路径携带该依赖。源码环境未安装时明确记录解析依赖缺失，仍独立读取 Steam Build ID，不影响对话及历史工具。

依据：开发者明确回复“同意 A”。现有依赖分组是否需要整体调整，尚未形成变更决定，不纳入已确认范围。

### 15. 删除独立 pi-probe 冒烟入口

删除 `lalc pi-probe` 命令、专用参数及仅供其使用的 `run_probe()` / `_interact()`，删除命令专用测试，更新当前使用文档并将原验证说明标为历史。保留正式 Agent 仍使用的 pi 启动、RPC、模型查询、证书环境、随包 pi 回退及 `pi_probe.ts` 工具扩展；本次不为命名而迁移共享模块。

共享启动、认证、额度、取消及权限边界的必要测试继续保留，实施时核对删除命令专用测试是否造成覆盖缺口。此命令删除后不再为其新增 Session、日志或版本索引。

依据：开发者明确回复“同意你的删除范围，加入到本次执行内容”。

## 整体确认

开发者阅读影响审查和实施收口后明确回复“同意”。索引采用 SQLite 标准库；标题复用已有规则，数量按去重 Session、时间按对应组合最近观测计算；按[影响审查](game-version-session-impact-review.md)实施。Windows 成品、跨 Unity 版本和真实模型 / 游戏验收不因本地测试通过而自动成立。
