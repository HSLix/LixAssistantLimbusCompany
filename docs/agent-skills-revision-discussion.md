# Agent Skills 修订讨论

2026-11-16。依据 Manifest 架构检查与整理修复的实际结果，逐项确认指导的修订范围。本文记录讨论决定，不表示 Skill 已修改或行为已验收；讨论收敛后先做影响审查，再实施。

## 已确认

### Step 按局部业务目标划分

Step 可以处理同一个局部目标所需的动作前、过渡中和完成后状态，例如“点击 Enter → 等待加载 → 确认进入编队”。不按画面数量强制拆分。多个独立业务阶段的选择和推进由 Task Workflow／Subworkflow 编排。

这将替换 workflow-conventions 中“Step 不能跨越多个状态”的绝对表述，保留 Step 的独立恢复、重新观察和完成确认职责。

### Step 显式交回，调用方统一处理未达成目标

Step 显式返回本次处理情况。调用方记录 Step 情况；目标未达成时计为无效循环，重新观察并完整分派，不要求针对每种异常落点编写专属处理分支。Workflow 的循环限制约束持续无效分派，避免无限空转。

这一决定允许将未达成目标交回上层统一处理，不等于把未达成报告为业务完成。

### 连续无效计数与总循环上限分开

每次 Step 交回且目标未达成都累计连续无效计数；只有 Step 确认本次局部目标达成才清零，仅识别到已知页面不清零。连续无效达到上限，由 Workflow 抛出失败。另保留不随局部成功重置的总循环上限，限制多个 Step 来回返回成功但整个任务无法结束的情况。

上述为业务流程计数，不是框架只读的 recovery_count；不改变其含义或清零规则。具体预算值及 Step 内失败边界仍待讨论。

### 正常网络过渡由 Workflow 集中处理

用户确认采用 Workflow 统一观察／分派入口识别 Connecting，并调用共用等待 Step 的方案；不在执行器内新增自动拦截，也不要求每个业务 Step 重复识别 Connecting。

业务 Step 未达成目标时显式交回；统一观察明确识别到 Connecting 时进入有独立上限的等待，结束后重新观察并完整分派。已确认的正常过渡不计无效循环；提示消失不证明原业务目标达成，不据此清零连续无效计数。仍保留独立总循环上限。

这一决定修正讨论中的建议“Step 内预算耗尽一律抛失败”（该建议未获接受）。普通业务 Step 的具体失败边界及预算值仍待确认。

### Connecting 等待超限后重新观察一次

共用等待 Step 达到独立等待上限时返回明确的 timeout。Workflow 重新截图：Connecting 已消失则正常重新分派；仍存在则抛出网络过渡等待超限失败，进入现有恢复流程，不再次启动一轮相同等待。

用户接受这一截止边界：失败依据是等待预算耗尽并在新截图中仍确认 Connecting；之后网络仍可能自行恢复，不能保证 Recovery Rule 检测时仍有匹配。该决定不改变执行器零匹配时的处理。

### 普通业务未达成统一交回，真正异常传播

普通业务 Step 有限尝试后尚未确认目标达成时，统一返回未达成及原因，包括入口不适用和局部超时。Workflow 重新观察，优先处理已确认的 Connecting；没有正常过渡时才累计无效循环，达到上限再抛失败。调用方无需针对每种交回原因单独处理。

参数不合法、工具执行错误等真正异常仍按原异常传播，不捕获成普通未达成。购买等不可安全重复的动作不得因重新分派而重复提交，重入必须先确认已有操作的结果。

### 通用基本 Step 参考一次短尝试，不强制所有 Step 同形

通用基本动作 Step 建议重新观察与检查适用性、执行一次动作、短暂等待、重新检测退出／完成信号，再返回本次情况。动作后建议至少等待 1 秒，也可等待 2 秒再检测；这是参考建议，不作为全部业务 Step 的硬性结构或统一时限。

首次生成不要求预先实现局部补点。只有后续发现原动作可能无效时，再考虑有证据支持且可安全重复的补点或替代输入，不能因暂未看到结果就认定输入未生效。专门业务 Step 允许其他适合其职责的形态；Connecting 等专用等待 Step 可保留有界轮询。

不再规定普通动作 Step 默认重试 3 次；普通短尝试的再次调度由 Workflow 控制。其他预算仍须有界，但具体值与单位待后续确认。

### 可交回动作 Step 的最小返回格式

新建或本次改造的可交回动作 Step 采用 `{"completed": true/false, "reason": "说明"}`。completed 仅表示该 Step 的局部目标已确认达成；reason 说明本次处理情况。仅在确有业务数据时增加字段。

Workflow 记录结果，并依据 completed 统一处理无效计数，不要求按 reason 编写分支。纯观察 Step、专用等待 Step 保留职责型返回契约。按需迁移既有 Step 并同步调用方，不强制迁移全部旧 Step，不将旧的 None 返回自动解释为未达成。

## 收敛状态

用户已确认共同理解并授权先影响审查、再实施仓库内置 Skills 与必要现行文档；不顺带迁移游戏 Manifest 或覆盖 Windows 用户 Skills。下文按讨论顺序保留变更过程，最终预算决定见文末，替代此前共享预算方案。

## 后续确认：统一循环分流及初始预算

用户选择 Workflow 当前统一采用循环分流，不采用讨论中提出的单向推进并存建议。每轮统一重新观察并分派，未命中适用分支时也计连续无效循环。

Task Workflow 总循环上限暂定 999 次，不随局部成功重置；连续无效循环上限初始为 3 次，无效时等待 1 秒后重新观察。确认 Step 局部目标达成才清零连续无效计数。已明确的正常 Connecting 过渡仍走独立有界等待，不计无效循环。

999 为 Task Workflow 的暂定循环次数，不是秒数，也不表示整场任务已验收；不据此擅自统一所有专用等待预算。Subworkflow 同样采用循环分流，其具体总预算尚未指定。

## 后续确认：集中处理已确认的正常加载

共用等待覆盖 Connecting 及已明确识别的 Combat Tips／Now Loading 正常加载画面，消失后重新分派。正常路径不再依赖 recovery.wait_combat_tips 等恢复规则等待这些过渡；真正的 Server Error 等错误弹窗仍由 Recovery Rule 处理。

仅凭可靠特征确认过渡，不能将黑屏、OCR 无结果或未知页面直接当作加载。此为拟修订指导及按需迁移原则，不表示现有 Manifest 已迁移或相关 Recovery Rule 已移除。

## 后续确认：共用等待初始预算

共用正常过渡等待初始最多观察 60 轮，轮间等待 1 秒，采用有界 for；后续依据实际日志调整。截图与识别也耗时，因此不是严格 60 秒。预算耗尽返回 timeout，由 Workflow 按已确认规则重新观察一次后决定是否抛失败。

## 后续确认：长流程共享兜底预算

用户提出并选择在 Plan Python 源码中，将 `MAX_LARGE_RETRIES` 初始值 999 写入 `ctx.run_state.settings`，供需要大量循环余量的长流程使用。该预算是很少触发的总循环兜底，用于限制过程确实很长，以及 Step 异常导致无效计数未发挥作用的情况；不替代连续无效循环限制，也不声称能识别全部无进展情形。

其他 Subworkflow 按自身职责设置总循环上限，不统一套用 999。此为本 Run 共享业务配置，不新增框架字段，不修改只读 recovery_count，不要求新增 GUI 配置页面。具体初始化及独立运行未经过 Plan 时的缺省行为待确认。

## 后续确认：共享预算初始化与缺省

Plan 使用 `ctx.run_state.settings.setdefault("MAX_LARGE_RETRIES", 999)` 初始化，不覆盖已有合法值。长流程独立试运行未经过 Plan 时，读取缺省值 999；已有值必须为正整数（不接受 bool），否则明确报错，不静默转换或替换。短流程仍使用各自总上限，不新增配置页面。

## 后续确认：按变更范围验证

不要求每次修改后完整游戏实跑。返回格式改动核对调用方和输出；分派／预算改动检查对应分支、无效计数及超限出口。修改 Candidate 后仍须 validate_and_publish；完整游戏路径在用户要求或变更确实需要时再跑。

未实跑如实报告；局部终点直接返回不能证明整场通过。删除 workflow-development 中无条件补一次完整试运行的要求，与 validation-and-trial 统一。

## 后续确认：配置页面询问范围

仅在新建／扩展需要从 Dashboard 启动的用户任务，且页面接线方式尚未明确时询问；内部 Step、Subworkflow、局部修复与 RunState 内部预算不因此询问或新建页面。用户已明确要求页面接线时按已有授权完成，安装仍保留专用审批。

## 用户补充：珍惜现场试运行，不堆砌状态检测

大部分现场只有一次低成本试运行验证机会：运行可能使游戏状态不可逆变化，再次验证可能需要重置副本并重新推进，或人工协助，两者成本都高。这是避免强行反复试运行的依据，不是每个任务只允许一次运行的硬性限制，也不是要求堆砌状态检测。

运行前明确本次起点、目标与应保留的证据；运行后利用实际日志和截图分析，不为重复验证擅自重置或消耗资源。确需复位时遵守已有授权及人工协助边界。

状态识别优先观察当前页面的标题、特色按钮等相对易识别且不易误识别的一个或几个特征。好的特征可能经过多次现场观察才能发现，允许依据新证据逐步改进，不要求首次一次找齐全部可靠特征，也不因试运行昂贵而追求大量冗余检测。

## 用户补充：复用 Asset 与临时识别 Step

选取特征前先查询当前 Asset 是否已有类似内容；命名应适度反映内容，便于检索。必要时创建只观察的临时 Step，验证当前页面是否命中、是否发生误识别及现有证据范围内的稳定性；不把当前页单次结果解释为跨场景验收。使用完成后可考虑通过 delete_component 清理，仍遵守当前工具权限、明确请求及专用人工确认，处理 Candidate 登记／引用，不删除历史发布源码。

## 最终决定：固定本地上限，不扩展 RunState

共享数据目前只有循环上限这一需求，用户决定不新增共享数据字段、不分离 RunState、不引入 workflow_limits，也不在 Plan 初始化共享预算。此前 MAX_LARGE_RETRIES 的共享、缺省及嵌套存储方案均不实施。

Task 在源码内设置固定的总循环上限。Skill 不规定具体总循环数字：对于可能需要大量循环的单次 Task，设置稍大且足够覆盖正常执行的上限，作为连续无效计数失效时的兜底；若实际证据说明不足，再增加。其他 Subworkflow 按各自职责设置有界总上限。连续无效初始 3 次、间隔 1 秒；共用正常过渡等待初始 60 轮、轮间 1 秒的决定保持。

## 实施补充：回归不限定 Skill 数量

用户明确要求 Skill 定向回归不限定总数量，允许人工增加 Skill。初始化检查保留必需内置入口，以当前完整资源树比较复制内容；已有用户添加的 Skill 应保留，空目录仍不自动补齐。新增参考目录参与递归复制与清理检查，不用固定入口清单的集合相等断言排除额外项。
