# 外部知识库同步与混合代码搜索：设计确认

2026-11-05。状态：主要设计边界已逐项确认，进入完整影响审查；已按确认设计接入本地实现，验证及验收边界见实施记录。开发者要求先 grill-with-docs 确认边界，再 design-impact-review，最后实施。本文记录确认结果，不表示代码已实现。

## 已确认

1. Git 参考仓库作为可覆盖的远端资料副本：成功 fetch 后由宿主固定对齐本次取得的 upstream 提交；不保留仓库内本地修改，自写资料放普通目录。不开放任意 reset 参数，不附带 git clean、自动 stash 或自动合并。此前已评估覆盖范围、取消后部分更新及版本报告风险，具体实施边界继续细化。
2. 保留当前 knowledge_search 字面搜索，codesearch 作为新增的混合搜索选择。混合搜索用于按意图寻找相关代码；字面搜索用于核对具体字符串，也支持在索引不可用时继续查资料。开发者于本轮逐项确认选择“保留字面搜索，新增混合搜索”。
3. LALC 管理自己的 codesearch 实例，使用专用配置与索引资源，只注册允许的外部知识库仓库，不共享用户已有实例。启动／停止时机以第 9、10 项为准；索引物理位置须遵守上游实际能力，见调研记录。
4. 开发者已确认名称为 knowledge_search_literal 与 knowledge_search_hybrid。前者保留当前不区分大小写的子串匹配语义，后者表达按相关性排序的混合检索。当前尚未改接口；旧历史工具记录如何展示、恢复及新请求如何声明，应在影响审查中覆盖，不自动授予旧名称新的能力。
5. 首版聚焦混合搜索与读取命中内容，暂不引入 find_impact 等符号影响分析及其项目分析辅助程序。读取采用代码块接口或现有 knowledge_read 尚未决定，需要结合版本一致性验证；限制工具暴露并不证明上游后台不会自动启动辅助进程，正式接入仍需核实并约束该行为。
6. 开发者明确要求将 fetch、reset 与索引更新视为一次完整更新：全部成功后才向 Agent 提供 B；任一步失败则继续提供此前可用的 A，向 Agent 明确报告并记录更新失败日志。不接受将工作区 B 与旧索引 A 当作一次成功更新。保留／恢复 A 的具体机制尚待研究，不能假定 reset 自身会完成索引更新，也不能假定失败的增量索引会保留完整 A。多仓库及首建失败分别以第 14、15 项为准；取消／崩溃恢复需技术验证。
7. 混合搜索的工具说明／Agent 使用指引建议优先用英文组织自然语言 query，并保留源码中的标识符原文；仍允许中文，不强制宿主翻译、不静默改写 query。本建议依据当前小样本的中英文 query 对比，不宣称所有中文检索均较差，也不据此确定最终嵌入模型。字面搜索仍使用需要查找的原文，不套用英文 query 建议。
8. 服务生命周期不绑定 Developer GUI 窗口，避免阻碍未来 Runtime Repair 复用。当前知识库工具仍仅授权 GUI 两种模式；未来复用生命周期机制不等于本次授予 Runtime／CLI 工具权限。此前每轮启动／停止的提议已由第 9 项替代。模型文件、持久索引／嵌入缓存与进程内缓存应分别描述，不能将重启后保留磁盘内容表述为保留全部缓存。
9. 开发者随后提出统一替代方向：pi 与 codesearch 均首次需要时启动、跨轮次复用、宿主退出时关闭；复用时若发现进程已中断，则重新尝试启动，失败按首次启动失败报告。此方向替代上一项“每轮开始尝试启动”的提议，以及此前按轮退出的建议。优先直观、少量且易维护的管理代码，不增加无需求的常驻监控、复杂恢复机制或重复检查。pi 跨轮复用还需核实既有按轮临时配置、历史注入、权限与取消机制；运行中断后的本轮重试／工具重放边界以第 10 项为准。
10. pi 在轮次开始、尚未发送本轮请求时发现旧进程已退出，可启动新进程继续；若在执行本轮请求途中退出，本轮报错结束，保留已有修改与日志，不自动重跑或重放工具。下一轮需要时再尝试启动；失败按首次启动失败报告。此项明确上一项待定的运行中断边界。
11. Windows 构建必须同时产出两种包：自带 Agent 功能包（包含 pi 与 codesearch）及不含 Agent 扩展的包，替代当前 with-pi／without-pi 的资源划分与命名。两包保持同一应用主体；模型及精简包规则以第 12、13 项为准。不将“自带 Agent”表述为包含远端推理模型或模型服务。
12. 无 Agent 扩展包仅不附带 pi、codesearch 与嵌入模型资源，不禁用 Agent 功能；仍允许调用用户自行准备的外部资源。两包共用相同应用主体，不另建功能裁剪分支。外部模型资源的定位方式及缺失反馈在实施前细化。
13. 自带 Agent 功能包同时提供默认量化 MiniLM 嵌入模型，配合英文 query 使用指引；普通使用期间不自动下载模型。模型缺失时明确报告混合搜索不可用。该模型仅负责检索嵌入，不是 Agent 对话模型；许可、固定资源清单和 Windows 离线加载仍须验证。
14. 多仓库按仓库独立更新：某仓库更新成功即可使用新版，另一仓库失败则继续使用其此前可用旧版；向 Agent 分别报告仓库版本及更新失败。不增加跨仓库整体回滚；每个仓库内部仍要求文件与索引对应同一可用版本。
15. 首次建索引失败、没有可用旧索引时，该仓库混合搜索不可用，仍保留字面搜索和读取；报告实际文件版本及建索引失败，不宣称混合搜索已就绪。
16. 开发者接受更新期间额外保留一套仓库文件与索引：保留 A，在独立 B 中完成 reset 和建索引，全部成功后整体切换。更新前必须检查实际目标磁盘空间，不足视为更新失败，保留 A 并向 Agent／调用方上传错误、记录日志，不能静默跳过或返回成功。预检需计入 B 副本、索引构建临时文件及同盘并存开销；预检不是空间预留，构建途中空间耗尽同样按更新失败处理。具体估算与磁盘空间无法查询时的失败诊断在实施中落实，不引入固定仓库大小上限。

## 调研输入与证据边界

- 上游：[flupkede/codesearch](https://github.com/flupkede/codesearch)。本次源码检查快照为 `b8ea0ccb50e6652c7ca364e47f044bea7cd2b86b`；实验候选为官方 `v1.7.9` macOS ARM64 基础包，程序报告 `1.7.9+1`，发布包 SHA-256 校验通过。源码快照不等同于发布包构建提交。
- README 及源码显示 semantic 路径包含向量、BM25 与标识符处理；literal 依赖索引及分析后的 token，不等于当前逐文件子串匹配。
- 多仓库服务提供 HTTP/MCP 与只读 REST 搜索接口。存在应用专用全局目录覆盖 `CODESEARCH_HOME`；这不自动保证注册范围、路径或模型执行边界符合 LALC 契约，仍需审查。
- 实验仅在临时目录准备两个代码库，共 14 个复制的 Python 文件，不扫描真实知识库、不注册到用户全局配置，不调用付费模型。默认模型首次准备遇到 Hugging Face 连接中断，重试后成功；小规模结果见[调研记录](external-code-search-research.md)，不代表实际参考仓库的效果验收。
