# 游戏输入接管与焦点等待：设计及影响审查

2026-11-07。设计讨论及源码审查记录；开发者已确认修订后的影响审查并授权实现。差距表保留实施前的源码检查结论，实施与验证单独记录。以下“已确认”表示本轮对话已接受的设计，不表示当前实现。保留工作区其他未提交修改，尤其 `tests/test_input_control.py` 中的既有变更。

## 已确认的设计

- 正式 Workflow 运行期间持续监听物理鼠标和键盘；注入事件不算用户输入，不屏蔽物理输入。
- 游戏在前台时，客户区内的物理鼠标按钮按下、滚轮，以及任意物理键盘按下触发接管暂停。键盘不要求鼠标位于客户区。移动鼠标、单纯释放按钮或按键、操作其他应用不新增接管暂停。
- `Ctrl+Alt+P` 在任意前台应用中都能暂停，等待中同样有效；已暂停后仍须显式恢复，不自动切换为继续。
- 准备发送游戏输入或取得游戏焦点前，若用户正在操作其他应用，等待连续 10 秒无此类物理活动。鼠标移动、点击、滚轮及键盘活动会重新计时。等待必须进入用户可见日志，且可暂停、取消。
- 首次启动例外（开发者已确认）：用户明确开始运行视为授权本次首次立即聚焦游戏；仍须先启动监听，再还原、聚焦，不等待 10 秒。明确点击运行窗口“恢复”同样豁免十秒等待，只等待物理输入释放及既有短暂安静检查；包含从暂停中继续游戏重启时的本次聚焦。其余自动重新聚焦及重启绑定仍遵守活动等待。
- 单纯失焦或最小化进入自动等待，无须手动恢复。满足空闲条件后允许还原、聚焦并继续。等待期间游戏已回到前台则立即继续；符合游戏接管条件的输入仍优先暂停。
- 输入尚未开始时，等待保留当前执行位置，不重跑 Step。已按住按键或触点的动作途中失焦时，先立即释放自动化持有的输入，等待后从当前 Step 开头重新执行；保留调用者帧及 Step 可重入约定。
- 窗口消失、身份变化、输入释放失败等不因新失焦策略放宽，继续使用各自现有安全处理；确认游戏进程退出仍由内置崩溃恢复负责。

## 确认的差距与影响路径

| 范围 | 检查到的当前行为 | 所需调整 |
| --- | --- | --- |
| `windows_input.py:WindowsInputBackend._listen` → `control.py:PhysicalInputMonitor.record/check_ownership` | 鼠标和键盘所有非注入事件共享一个代次，既不区分移动、按下、释放，也不判定前台或客户区 | 分开记录活动时间和接管信号；鼠标按事件坐标判断客户区及前台，键盘按事件时前台判断；热键独立于目标前台识别。回调仍只做轻量记录，不写日志、不等待 |
| `control.py:InputSession.check/prepare_resume/wait_quiet/execute` | 失焦及最小化作为 `WindowError` 转为手动暂停；恢复只有 0.3 秒全局安静检查；`any_pressed()` 会把其他应用中的按住输入也转成接管 | 新增自动等待与手动暂停的区别；其他应用的输入或长按只能延后取得控制权，不能误报游戏接管；明确手动恢复不等待十秒，自动重新聚焦遵守十秒规则 |
| `application.py:_start_session/_ensure_input_session` → `focused.py:connect` | 首次连接先聚焦，再建立输入监听；首次聚焦时监听尚未建立 | 正式 Run 首次聚焦前建立监听；明确开始运行时首次立即聚焦，不等待 10 秒。运行中的后续聚焦不得继承此例外 |
| `focused.py:WindowsWindowPlatform.focus` | 立即还原并调用 `SetForegroundWindow`，然后等待真实焦点 | 正式 Run 自动重启绑定及运行中自动重新聚焦须先经过活动等待；在还原和聚焦前复核。明确开始运行和手动恢复所需的一次聚焦豁免十秒等待 |
| `control.py:_key/_touch/_wait/_release` → `runtime.py` Step 中断边界 | 长动作轮询窗口；`finally` 保证释放，但失焦当前走手动恢复 | 保留释放失败终止边界；区分“动作前等待”和“动作已开始后失焦”，后者释放后自动等待并重入当前 Step，不能在持有输入时等待 10 秒 |
| `application.py` 截图、保存、匹配、OCR → `focused.py:check/capture` | 观察路径也检查前台；部分先调用窗口检查，失败后才调用输入检查 | 所有正式 Run 观察入口使用一致的失焦等待策略；等待跨越失焦时明确旧截图失效和重新观察顺序，不能恢复后沿用失效图或抛出等待前的旧失焦异常 |
| `game_restart.py:checkpoint/bind_checkpoint/bind` | 过渡期按住任意输入也暂停；新窗口绑定会聚焦；启动绑定有 60 秒时限 | 无窗口时仍保留全局暂停热键和活动监测；绑定前等待不能重复启动游戏，也不能把正常用户活动当作接管 |
| `run_logs.py:read_page`、`control.py:emit` | 用户日志接受 `component_log` 和 Action 结束事件，现有 `input_quiet` 不会作为普通日志显示 | 复用 Info `component_log` 写等待开始、结束及实际耗时、结束原因；按需汇总计时重置，避免鼠标移动每次刷屏。暂停、取消也须有等待结束记录 |

`runtime.py:RunGate` 当前提供暂停/恢复/停止，检查到的正式输入监听路径没有专用全局暂停热键识别；本次需补齐，不能把普通键盘接管当作全局热键已经实现。

## 已批准的实施细节

1. 为避免用户持续活动把正常焦点等待误判成重启失败，用户活动等待时间不计入重启的窗口绑定超时，计入实际运行耗时与等待日志；真正的窗口启动/绑定等待仍有原时限。
2. 本次范围为正式 Top-level Execution（含 GUI/CLI、Developer Trial）。独立截图、素材调试等非 Workflow 操作不扩展成 Run，也不在无运行时安装全局暂停监听。各入口明确开始运行及手动恢复时均只授予本次聚焦例外。

## 潜在风险与验收限制

- 低级钩子的点击激活时序、覆盖在游戏上的其他窗口、客户区边缘及 DPI 换算需要 Windows 实测；以事件发生时真实前台和坐标为准，不能仅检查鼠标矩形范围。
- 物理事件、焦点取得与输入注入之间存在竞争；应在最后输入边界复核，仍需 Windows 验证。注入输入不得更新物理活动或误触热键。
- Step 重入可能重做已完成的业务前缀，是开发者已接受的长动作失焦处理代价；不新增低级动作续传或任意 Workflow 状态恢复。
- 审查阶段仅有源码证据；实施后自动检查结果见下节。真实 Windows、成品包及真实游戏仍未验收。

实施顺序：先统一监听及信号语义，再接入初次连接/等待/热键和长动作边界，随后覆盖观察与重启入口，补日志及针对性测试，最后同步现行文档并运行普通回归。开发者已明确要求纳入手动恢复例外后开始实现。运行窗口暂停控件旁显示“全局快捷键：Ctrl Alt P”，沿用启动语言翻译。


## 实施与验证

开发者确认手动恢复例外后授权实现，现已完成本地代码与文档更新：

- 只读钩子按事件类型、真实前台、客户区及命中窗口筛选接管；注入事件不更新物理活动或热键。其他应用活动与游戏接管代次独立记录。
- 聚焦前监听，明确开始运行立即聚焦；原生首次聚焦仍在等待时也能响应全局暂停。运行中失焦或最小化自动等待，明确恢复只等待输入释放和原有短暂安静检查。
- 长动作失焦先释放，再由 Step 边界自动等待并重新执行，不进入手动暂停或业务恢复规则；真正接管和热键仍等待人工恢复。恢复过程中再次按热键会保持暂停。
- 截图跨失焦会重新捕获，保存证据路径跟随实际 observation；OCR 若原图在等待后更新则重新识别，避免将旧结果关联到新图。
- 重启绑定共用活动等待及阶段内暂停，用户活动等待不消耗绑定时限，不重复启动游戏。等待开始、结束、实际耗时和结束原因以 Info `component_log` 展示。
- 正式运行和 Developer Trial 共用的 `TrialDialog` 显示全局暂停快捷键提示；中文为“全局快捷键：Ctrl Alt P”，英文随启动语言显示。
