# Run 列表与聊天卡顿影响审查

## 本次确认的设计

2026-11-19 用户确认 `list_runs` 从嵌入完整 Run Result 改为分页返回终态摘要。摘要保留失败码、Plan 任务总数和全任务成功标志（以原始记录存在的字段为准）。外层保留状态、失败原因和现有分页。按 Run ID 查阅 Execution Trace 可取得原始证据。这里的摘要是检索接口，领域术语 Run Result 仍指执行器的完成记录。

用户同时确认聊天中的大工具详情显示有长度上限的预览，并可主动复制完整 JSON。该限制只用于界面排版。原始 Tool Result、诊断日志和 Sharing 历史无需迁移。

## 日志证据

导出的第一轮使用 DeepSeek，压缩触发线为 400,000 token。事件 30 的 `list_runs(limit=10)` 文本是 1,902,893 字节。其中 Run 348 的结果约 1.84 MB，包含 10,000 个任务项。事件 40–58 记录 496,493 → 17,855 token 的压缩，耗时约 51 秒，计入 6 次压缩请求。工具调用与压缩都在同一对话轮内。

Run 352 的 4 次查询均返回，最大的工具文本约 34 KB。另一次覆盖全部 Run 的搜索耗时约 63 秒，返回约 3.3 KB，体现扫描耗时与结果体积是两件事。14:36:40（UTC+8）发布成功，第 13 次模型请求随后发出，最后记录停在该响应的 `message_start`。压缩早已完成，最后一次请求体约 217 KB，估算为 56,329 / 400,000 token。导出证据没有第 13 次请求的完成或错误事件，也不包含 Windows 卡死现场的主线程栈。不能把 Run 352 的 OCR 查询认作这次中断的直接原因。

用原始工具结果在 macOS 离屏 Qt 中复现：详情折叠时渲染约 3 ms，展开后每次完整重绘约 7.3–7.5 s。原界面的计时器、状态和流式更新均可能重新排版同一展开内容。

Windows 用户按折叠／展开旧工具详情的流程复测。`uv run lalc` 启动的开发者面板属于 `python` 进程。14:55:53.980 窗口仍响应，14:56:01.773 至 14:56:07.215 三次采样为未响应，14:56:09.926 恢复。期间 Agent 最新日志始终为 14:52:09.267 的 `round_finished`，未响应期间有一次采样记录 7.77 CPU 秒增量。结合离屏排版复现，确认旧聊天详情能在 Agent 本轮已结束时引起 Windows 界面卡顿。原始强制退出当时的展开状态和线程栈未采集，仍无法确认两次是否完全同因。

## 影响与验收

- `run_logs.run_summary` 从原始首尾事件投影字段。Developer Agent 与远程 MCP 共用 `RepairTools.list_runs`，因此两边的列表都采用新摘要。读取终态事件仍要解析原始 JSON 行，改动主要消除重复传输和模型上下文开销。执行结果和现有 Trace 读取工具保留完整信息。
- pi 工具描述、Agent 提示和工具文档同步引导先查摘要，再按选定 Run 的任务名或失败码缩小 Trace 查询范围。显式查询巨大终态事件仍可能占用大量模型上下文。
- `RepairChat` 在展开时最多排版 16,000 字符，复制使用同一份详情数据。旧聊天中的大结果也受益。原样本重算列表后为 4,014 字节，修复后旧结果在 macOS 离屏展开约 28–46 ms。Windows 已确认卡顿复现，修复版仍待同样步骤验证。
