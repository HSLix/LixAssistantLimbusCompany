# Use immutable saved manifests with mutable top-level working manifests

Registered Task Workflows, Subworkflows, Steps, Recovery Rules, and Trusted Actions are immutable Components. A Component ID is `sha256:` followed by the SHA-256 of the exact source bytes, so identity and source-integrity verification use the same value and no separate source-hash field exists. Each Manifest is one complete document whose `components` mapping resolves stable dotted logical names to immutable Task Workflow, Subworkflow, or Step Component IDs; the source file's single role decorator remains the authority for which of those three roles each entry has. Dedicated `recovery_rules` and `trusted_actions` mappings register their distinct loading paths. Every Trusted Action entry explicitly records its single `observe` or `control` `classification` for the executor's non-configurable access matrix. Its `assets` mapping instead records semantic names, languages, shared relative paths, and complete content hashes; Assets have no Component IDs. Editing an eligible executable capability changes its Component ID and changes the value at the same logical name instead of overwriting content or creating a per-component version sequence. The Agent may modify Steps, Task Workflows, and Subworkflows, but not Trusted Actions, Recovery Rules, or Assets in this scope. Exactly one retained Manifest is the Default Manifest used when a new start request does not name another Manifest. The selected Manifest becomes that Run's Base Manifest. Every complete Manifest used for an attempt is durably retained by Manifest ID, and the executor atomically selects the complete version for this execution. An existing Manifest selected for another attempt retains its ID; Trace records the separate attempts. Recovery may select any earlier retained Manifest ID directly instead of replaying approval history.

## Consequences

- The first version executes no Temporary Action Plan. An Agent proposal may change Steps, Task Workflows, and Subworkflows together, but selection requires a legal fresh invocation of the paused current Step. Changed Components use the ordinary execution path after the whole Manifest is selected.
- Later Task Workflows in the same sequential Automation Plan may reuse capabilities added earlier in that Top-level Execution; parallel Task Workflow execution is excluded from the first version.
- The current Working Manifest is persisted so it survives process failure; review differences from its base are derived when needed.
- A Working Manifest update becomes visible only while the executor is paused and can immediately arrange a legal fresh Step call. The complete replacement and referenced sources are written and verified before one atomic switch. Every attempted complete Manifest remains available by Manifest ID. A failed current-Step attempt pauses for another choice or termination rather than automatically rolling back; existing Python frames are never hot-patched.
- Manifest loading is uniform across Task Workflows, Subworkflows, Steps, Recovery Rules, and Trusted Actions rather than being specialized for Step replacement. A complete Manifest is loaded once after validation; calls do not reread Component source from disk. After a Manifest switch, Components that have not yet been entered resolve to the newly loaded implementation.
- Successfully loaded trusted modules are reused within the process by immutable Component ID. Selecting another Manifest rechecks the stored source bytes against that ID and reuses the existing module when the ID is unchanged; it never reloads by logical name or uses `importlib.reload()`. Old modules may remain until process exit because entered Python frames can still reference them. This cache contains no logical-name registry; source is always verified against its immutable Component ID before ordinary execution.
- Developer-authored source keeps meaningful filenames before publication. An entry in a candidate Manifest contains either an existing `component_id` or a `source_path` for new or edited source, never both. A source path is relative to the candidate Manifest's directory; absolute paths and resolved paths or symbolic links that escape that directory are invalid. Saving or approving resolves every source path, computes the missing Component ID, copies the exact bytes to `components/<sha256>.py`, and writes a saved Manifest containing only Component IDs. Every saved Manifest requires complete Component IDs and rejects source paths; the loader derives each formal source path from its ID. Runtime permission for Agent-proposed source is recorded separately from permanent publication.
- A candidate Manifest must not contain `manifest_id`. Publishing assigns a UUID `manifest_id` and creates `manifests/<manifest_id>.json` without overwriting an existing file. `manifests/default.json` contains only the Default Manifest ID and changes only through a separate explicit selection. Manifest identity is independent of Component content identity.
- Publishing validates and loads the complete candidate, then writes immutable Component files and the saved Manifest without changing `manifests/default.json`. Selecting a Default Manifest validates and loads any existing saved ID before atomically replacing that pointer; an ID without permanent approval first requires a warning and explicit confirmation. A failure or declined confirmation leaves the previous Default Manifest selected. Successfully written but unreferenced immutable files are retained for later reference-based cleanup rather than deleted as rollback. Unexpected exceptions during validation, load, publishing, or Default selection are logged at `error` with their failing phase and traceback; ordinary validation rejection remains a structured validation result rather than a system-error log.
- Candidate and saved Manifests require integer `schema_version: 1`. Missing or unsupported versions are validation errors; the first implementation neither guesses a format nor migrates older data. The complete top-level shape includes `components`, `recovery_rules`, `trusted_actions`, and `assets`, with `assets` required to remain empty until its implementation slice.
- The main process loads shipped Components and Agent-proposed Steps or Workflows after complete validation and explicit supervised permission for this execution. Permission is recorded outside the Manifest data; a self-declared field cannot grant it. Importing executes module-level Python and may have side effects. Ordinary execution is not a security sandbox, and permission for one execution does not grant permanent publication.
- Agent-generated source is completely validated and shown for explicit permission before execution in the current run. Once selected, its Steps and Workflows use the ordinary Component path. This path is not a security sandbox, and `importlib.reload()` is not used for Component replacement. Runtime permission and post-execution permanent publication are separate.
- Manifest validation returns every independently determinable error with a stable code, human-readable message, logical name, and source position when available. A failed prerequisite suppresses only dependent checks for that source instead of producing cascading errors. Any static error prevents all module imports; after a clean static pass, import failures for trusted Components are also collected. Any error publishes nothing and leaves the Default Manifest unchanged.
- Manifest parsing is strict for its declared schema version: duplicate JSON keys, unknown top-level or entry fields, missing required fields, and wrong field types are errors. The loader neither ignores nor autocorrects fields; later additions require an explicitly supported schema version.
- Schema version 1 requires the top-level `assets` field, but #308 accepts it only as an empty object. Non-empty Asset entries remain invalid until the later Asset slice defines and validates their complete contract.
- Stable logical names consist of one or more case-sensitive Python identifiers separated by `.` and are unique across `components`, `recovery_rules`, and `trusted_actions` within one complete Manifest. Lowercase is only a naming convention; the loader neither rewrites a name nor infers a Component role from it. Separate mappings select loading and validation rules but do not create separate logical-name namespaces.
- Multiple logical names may reference the same Component ID. When a Trusted Action Component ID is referenced more than once in one Manifest, every reference must use the same `classification`; one immutable implementation cannot receive different observe/control permissions through aliases.
- A paused Step wrapper retains its logical name, original arguments, and return contract. Re-entry resolves the latest Component ID at that name; Trace records the name and actual Component ID. No replacement chain is required.
- Trace records the Manifest ID used by each attempt and the formal Components actually executed with their Component IDs, evidence, and Agent Interaction Log references. The complete attempted Manifests remain durable under their IDs; no separate Working Manifest content hash is needed.
- During a Top-level Execution, every attempted complete Manifest remains available by Manifest ID. At execution end, only the current Working Manifest is offered for permanent review when its ID has not already received permanent approval; returning to the Base Manifest or another approved ID skips repeated approval, and intermediate attempts are not separate approval candidates. The first version has no partial Component or file approval.
- Approving an Agent Capability Proposal grants permanent publication to the reviewed complete Manifest ID; it never mutates the Base Manifest, creates a duplicate of the selected Manifest, or changes the Default Manifest implicitly.
- Publishing a user-edited Manifest creates a new retained Manifest. Selecting an existing Manifest as Default creates nothing new.
- Manifests are shown newest first. Only a non-default, non-sole Manifest may be deleted, and deleting it does not automatically delete Components.
- Every retained Manifest is a Recovery Point. Components referenced by a retained Manifest or durable Working Manifest cannot be cleaned up.
- A mutable Component Usage Index records `last_used_at` when a Component is actually executed or read. Only unreferenced Components are cleanup candidates; elapsed time since actual use helps identify or order candidates but never authorizes deletion of a referenced Component.
- Cleanup only presents candidates for user-initiated deletion. It never deletes by elapsed time, and it must recompute all retained-Manifest and durable-Working-Manifest references immediately before deleting.
- Approval history is not a recovery mechanism. Retained Components and manifest snapshots are sufficient.
