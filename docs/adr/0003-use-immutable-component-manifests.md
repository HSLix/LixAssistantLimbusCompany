# Protect saved manifests from Agent modification and select complete working manifests

Existing Manifest and Asset files must not be modified, overwritten, renamed, or deleted by the Agent. Agent repairs create new Asset files and a new complete candidate Manifest; candidate mappings may reference different Asset files without editing existing files. Human management and modification of existing Manifest and Asset files may be provided by a future GUI; that capability and its reference/hash handling are deferred and are not implemented in this version. For Manifests and Assets, this is an Agent permission boundary, not a permanent prohibition on human edits.

This restriction also applies to Agent-generated code and executor operations performed on the Agent's behalf: neither may overwrite existing Manifest or Asset files. Adapting a template means saving a new Asset file and publishing a new complete Manifest with updated path/hash mappings; existing files and their recorded mappings remain unchanged. The possibility that an Agent edits an old image and invalidates an old Manifest's hash is outside the permitted repair behavior, not a case the repair path should support. Human edits through a future GUI remain a separate deferred feature.

## Consequences

- The first version executes no Temporary Action Plan. An Agent proposal may change Steps, Task Workflows, and Subworkflows together, but selection requires a legal fresh invocation of the paused current Step. Changed Components use the ordinary execution path after the whole Manifest is selected.
- Later Task Workflows in the same sequential Automation Plan may reuse capabilities added earlier in that Top-level Execution; parallel Task Workflow execution is excluded from the first version.
- The current Working Manifest is persisted so it survives process failure; review differences from its base are derived when needed.
- A Working Manifest update becomes visible only while the executor is paused and can immediately arrange a legal fresh Step call. The complete replacement and referenced sources are written and verified before one atomic switch. Every attempted complete Manifest remains available by Manifest ID. A failed current-Step attempt pauses for another choice or termination rather than automatically rolling back; existing Python frames are never hot-patched.
- Manifest loading is uniform across Task Workflows, Subworkflows, Steps, and Recovery Rules rather than being specialized for Step replacement. A complete Manifest is loaded once after validation; calls do not reread Component source from disk. After a Manifest switch, Components that have not yet been entered resolve to the newly loaded implementation.
- Formal runtime modules are loaded from the immutable stored hash file and may be reused by Component ID. Developer Candidate imports remain separate and cannot satisfy this formal cache; source locations and traceback filenames must identify the immutable stored file.
- Successfully loaded trusted modules are reused within the process by immutable Component ID. Selecting another Manifest rechecks the stored source bytes against that ID and reuses the existing module when the ID is unchanged; it never reloads by logical name or uses `importlib.reload()`. Old modules may remain until process exit because entered Python frames can still reference them. This cache contains no logical-name registry; source is always verified against its immutable Component ID before ordinary execution.
- Developer-authored source keeps meaningful filenames before publication. An entry in a candidate Manifest contains either an existing `component_id` or a `source_path` for new or edited source, never both. A source path is relative to the candidate Manifest's directory; absolute paths and resolved paths or symbolic links that escape that directory are invalid. Saving or approving resolves every source path, computes the missing Component ID, copies the exact bytes to `components/<sha256>.py`, and writes a saved Manifest containing only Component IDs. Every saved Manifest requires complete Component IDs and rejects source paths; the loader derives each formal source path from its ID. Runtime permission for Agent-proposed source is recorded separately from permanent publication.
- A candidate Manifest must not contain `manifest_id`. Publishing assigns a UUID `manifest_id` and creates `manifests/<manifest_id>.json` without overwriting an existing file. `manifests/default.json` contains only the Default Manifest ID and changes only through a separate explicit selection. Manifest identity is independent of Component content identity.
- Publishing completes static candidate validation, stores immutable Component source, and loads the formal implementations from those stored hash files before saving the complete Manifest; it never changes `manifests/default.json`. Developer validation imports cannot be reused as the returned formal implementations. Selecting a Default Manifest validates and loads any existing saved ID before atomically replacing that pointer; explicit selection requires no additional confirmation, regardless of permanent approval status. A failure leaves the previous Default Manifest selected. Successfully written but unreferenced immutable files are retained for later reference-based cleanup rather than deleted as rollback. Unexpected exceptions during validation, load, publishing, or Default selection are logged at `error` with their failing phase and traceback; ordinary validation rejection remains a structured validation result rather than a system-error log.
- The main process loads shipped Components and Agent-proposed Steps or Workflows after complete validation and explicit supervised permission for this execution. TODO after the first release: evaluate moving executor execution into a subprocess and the required Context transport, cancellation, and original-error propagation; the current version keeps main-process loading and execution. Permission is recorded outside the Manifest data; a self-declared field cannot grant it. Importing executes module-level Python and may have side effects. Ordinary execution is not a security sandbox, and permission for one execution does not grant permanent publication.
- Agent-generated source is completely validated and shown for explicit permission before execution in the current run. Once selected, its Steps and Workflows use the ordinary Component path. This path is not a security sandbox, and `importlib.reload()` is not used for Component replacement. Runtime permission and post-execution permanent publication are separate.
- Manifest validation returns every independently determinable error with a stable code, human-readable message, logical name, and source position when available. A failed prerequisite suppresses only dependent checks for that source instead of producing cascading errors. Any static error prevents all module imports; after a clean static pass, import failures for trusted Components are also collected. Any error publishes nothing and leaves the Default Manifest unchanged.
- Manifest parsing is strict for its declared schema version: duplicate JSON keys, unknown top-level or entry fields, missing required fields, and wrong field types are errors. The loader neither ignores nor autocorrects fields; later additions require an explicitly supported schema version.
- Stable logical names consist of one or more case-sensitive Python identifiers separated by `.` and are unique across `components` and `recovery_rules` within one complete Manifest. Lowercase is only a naming convention; the loader neither rewrites a name nor infers a Component role from it. Separate mappings select loading and validation rules but do not create separate logical-name namespaces.
- Multiple Component logical names may reference the same Component ID. Trusted Actions have no Manifest IDs or aliases; their application registration fixes the observe/control classification.
- A paused Step wrapper retains its logical name, original arguments, and return contract. Re-entry resolves the latest Component ID at that name; Trace records the name and actual Component ID. No replacement chain is required.
- Trace records the Manifest ID used by each attempt and the formal Components actually executed with their Component IDs, evidence, and Agent Interaction Log references. The complete attempted Manifests remain durable under their IDs; no separate Working Manifest content hash is needed.
- During a Top-level Execution, every attempted complete Manifest remains available by Manifest ID. At execution end, only the current Working Manifest is offered for permanent review when its ID has not already received permanent approval; returning to the Base Manifest or another approved ID skips repeated approval, and intermediate attempts are not separate approval candidates. The first version has no partial Component or file approval.
- Approving an Agent Capability Proposal grants permanent publication to the reviewed complete Manifest ID; it never mutates the Base Manifest, creates a duplicate of the selected Manifest, or changes the Default Manifest implicitly.
- Publishing a user-edited Manifest creates a new retained Manifest. Selecting an existing Manifest as Default creates nothing new.
- Manifests are shown newest first. Every retained Manifest is a Recovery Point, and its referenced files remain available.
- Resource deletion, reference scanning, Component Usage Index, and cleanup UI are deferred for future discussion under ADR 0021. Earlier deletion eligibility, usage timestamp, and reference-recheck proposals are not first-version requirements; no maintenance policy or interface is committed here.
- Approval history is not a recovery mechanism. Retained Components and manifest snapshots are sufficient.

## Current format and lifecycle

Use schema version 2: Candidate Manifest fields are `schema_version`, `components`, and `recovery_rules`; saved Manifests also contain UUID `manifest_id`. Embedded Asset and Trusted Action mappings and old versions are rejected without migration. Application registration owns Trusted Actions; each Manifest owns a separately published Asset Library loaded in full alongside its Components. Developers edit only the Candidate library and publish a new Manifest/library pair. Images use complete SHA-256 filenames and are never overwritten. Every formal Run connects and focuses the Target Window and starts input monitoring before execution; one Plan shares the session until cleanup.

See the Stage 2 execution contract's current Manifest, Asset and Run boundaries, ADR 0023 and ADR 0024 for storage, confirmation and publication details. Existing repository examples are removed; tests own their Component fixtures and action callables.
