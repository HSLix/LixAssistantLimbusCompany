# Use Python Workflows with Centralized Exception Control

2026-10-27：后续 [ADR 0032](0032-use-python-plans-and-coexisting-user-developer-guis.md) 接受每 Manifest 唯一 Python Plan、同进程双 GUI 和 Candidate Plan 编辑/已发布试运行，按其列明范围替代本文的旧 Plan/GUI 边界；本文其余决定及历史实施证据保留，Stage 4 尚未实现。

Task entry `condition` and independent final `verify` callbacks are removed. This decision supersedes the earlier proposal to extend recovery to those callbacks. Entry checks and business-result validation belong in ordinary Steps; only Step has a recoverable continuation.

LALC models Task Workflows, Subworkflows, and independently recoverable Steps as immutable Python Components. Python supplies control flow, local variables, returns, and the call stack; this replaces the explicit YAML Step graph and avoids maintaining a growing custom Workflow language and interpreter. Each formal Component uses a typed `execute(ctx, *, ...)` signature as its sole input contract. Only Step may expose a matching read-only `condition(ctx, *, ...)`; Task Workflow and Subworkflow expose only `execute`; Trusted Actions provide low-level screenshot, recognition, input, and wait operations. Input annotations recursively support JSON scalars, `Literal`, optional values, `list[T]`, and `dict[str, T]`, with JSON-compatible defaults; arbitrary classes, Pydantic models, Enum types, sets, tuples, and non-optional unions are excluded. This supports UI and Agent inspection without an independent input schema or `ctx.inputs`. A module docstring is the sole natural-language Component description and is read by parsing source; there is no independent `description` field.

Exactly one parameterless `@task_workflow`, `@sub_workflow`, or `@step` on each Workflow or Step entrypoint is the sole source of its `ctx.call()` role. After verifying the source bytes against the Component ID, the loader parses that decorator and binds the stable logical name from the Manifest. These entries do not repeat `component_kind`, and paths, filenames, logical-name prefixes, and tags never infer role. Recovery Rules do not add a fourth decorator: they are immutable Components registered in a dedicated `recovery_rules` mapping with fixed `detect(ctx) -> bool` and `recover(ctx) -> None` entrypoints and are invoked only by the executor. Task and Sub Workflow wrappers write the same Ledger record shape with `workflow_kind = task | sub` and final `success | failure`: Subworkflow normal return is success and any non-normal exit is failure, without a verifier. Safe Task Termination is performed and counted only on the owning Task record rather than duplicated on active Subworkflows. Subworkflow calls use the ordinary Python stack and their wrappers add no recovery mechanism.

One terminal cause propagates the same originating `failure_code` to every active Workflow record unwound by it. Ancestors are not translated to generic child-failure codes; their messages, parent-call identities, and Trace links retain the actual source, while already returned Subworkflows remain successful.

One Agent invocation is one Trace event and is attributed to the owning Task Workflow plus the active Subworkflow, if any, whose call span contains it. Those successful spans are Agent-assisted; already returned and sibling Subworkflows are unaffected. Per-Workflow counts are intentionally overlapping health observations, so application-wide Agent totals use unique Trace events rather than sums across overlapping Ledger records.

Public Recovery Rule attempts and results and Step reinvocations use the same span attribution. Deterministic recovery alone does not change a successful span from strict to Agent-assisted. These per-Workflow recovery counts measure Component reliance and intentionally overlap; application-wide totals again come from unique Trace events rather than nested Ledger sums.

Each Task Workflow, Subworkflow, or Step occupies exactly one Python source file containing one decorated `execute` entrypoint and a concise module docstring. Only Step may additionally expose a matching read-only `condition`; Task Workflow and Subworkflow define neither `condition` nor `verify`. Legacy callback declarations are rejected with a migration message rather than silently ignored. Recovery Rules use fixed `detect` and `recover`; application-registered Trusted Actions use their Python signatures, and the Manifest cannot configure function names. Formal Components import only the standard library and LALC public Runtime API; Trusted Actions may additionally import dependencies fixed by the shipped environment. Components never share a source file or import another Component implementation.

Formal Task Workflow, Subworkflow, Step, Step condition, Recovery Rule, and every private function in their source files contain no `except`. The loader rejects exception handlers without reachability or type analysis. `try/finally` remains legal for cleanup, but `return`, `break`, `continue`, and `raise` are forbidden throughout finally suites. All callable phases use one invocation mechanism to record identity, copied inputs, results, timing, and original errors. An existing `ExecutionFailure` is recorded then propagated unchanged; raw non-user errors are normalized once with their original cause and complete traceback. Expected absence remains an ordinary result. Trusted Actions may catch low-level errors only without hiding evidence or fabricating success. Recovery Rule errors never recursively recover themselves.

User pause, physical takeover, and cancellation are user control requests, not execution failures. Ordinary Pause uses the cooperative Run Gate; when stack unwinding is needed, the executor uses the single internal signal family `UserInterruption` and retains the requested intent. Pause or takeover waits for explicit manual Resume; cancellation ends execution and prevents later Plan items. A shared signal name never turns cancellation into resumable pause. User signals are handled before generic task failures and bypass automatic Recovery Rules and Agent handling. A cancelled Task record, when one already exists, may still record `failure_code: user_cancelled` as its terminal result; this does not make the signal an `ExecutionFailure`. `safe_termination_performed` reports only an action actually performed. Control signals cannot be swallowed by formal source.

Workflow and Step Components call one another only through literal `ctx.call(logical_name, **arguments)`. Each call resolves the latest Working Manifest and reuses its verified immutable loaded implementation without disk rehashing. Only Task Workflow may call Subworkflow or Step; Subworkflow calls only Step; Step calls no formal Component. Step condition and Recovery Rule entrypoints also call no formal Component. Trusted Actions use literal `ctx.action()` and the executor rechecks the actual caller phase and application-registered observe/control classification. Task and Subworkflow execute, Step condition, and Recovery Rule detect use observe only; Step execute and Recovery Rule recover use both. Wait is control. Static validation checks direct visible violations throughout source; runtime dispatch is authoritative for indirect helper calls. No permission inheritance, configurable policy registry, generated wrappers, or direct model-action channel is introduced. Agent proposals cannot change Trusted Actions or Recovery Rules during a Top-level Execution.

A runtime Trusted Action access violation is an `ExecutionFailure`, rejected before the forbidden action. Its diagnostics identify the caller logical name, Component ID, execution phase, attempted function or action, and the reason it is forbidden; the original Python traceback must retain the exact source file and line of the offending call, including indirect private-function calls. This is not a user interruption and needs no additional exception taxonomy. Like other ExecutionFailure cases, a Step-local access violation enters the Step recovery boundary; any recovery must still obey the fixed permissions and cannot grant the forbidden operation. Agent repair still requires a paused Step and a compatible fresh invocation; outside a Step or after final verification no lost frame is reconstructed.

Asset access is confined to the Trusted Actions that consume it. Formal and temporary Python pass a stable semantic name such as `ui/popup/confirm`, never a language, extension, or path. The Trusted Action uses `ctx.game_language` and the current Working Manifest's dedicated Asset Library to verify and match a shared-library file, with deterministic cross-language fallback when the current language is absent. Assets are content-hashed shared files rather than Components and have no Component IDs or `ctx.asset()` interface.

Run Context is an executor-owned runtime interface, not a business-data store. It exposes component invocation, Target Window and language access, Working Manifest resolution, Trace, evidence, cancellation, and non-time execution budgets; only the executor, wrappers, and Trusted Actions manage its internal state. Formal Components have no arbitrary mutable Context fields, shared task dictionary, or generic update API: inputs, loop values, intermediate business results, and outputs use named parameters, ordinary returns, and local variables. `ctx.call()` normalizes inputs and supplies independent copies; startup and Step-boundary snapshots remain immutable for verification and fresh invocation. A Subworkflow returns any scheduling suggestion for its Task Workflow caller to apply. External game state is re-observed rather than inferred from memory, and the Agent receives only a JSON diagnostic snapshot assembled from explicit values and runtime records, never the live Context. No child Context or merge mechanism is introduced.

Repeated goals remain ordinary Task Workflow loops over Subworkflows and Steps, with completion data in parameters, ordinary returns, and local variables. Task Workflow normal return after JSON-compatible result validation records success; no independent verifier is required or executed. It is recommended that authors check meaningful preconditions and final business outcomes in explicit Steps before returning. A failed check raises `ExecutionFailure` in that Step and uses the ordinary recovery path. This is author guidance, not a special verification callback or executor-enforced business predicate. The executor never fabricates results or progress. Failure codes, messages, complete traceback, and cause/context chains propagate from their source without reinterpretation by intermediates; adding caller or phase evidence does not change their meaning. Reporting the correct cause is a source-code and review responsibility, not a runtime truth-verification system. A reporting code never proves that Safe Task Termination was performed. Trace is diagnostic evidence, not a business-data channel.

Automation Plan is user-saved configuration containing an ordered list of Task Workflow logical names and explicit input dictionaries. Before any task starts it parses and validates the whole list and reports independent preflight errors together; failure starts no Task and contributes no Task statistics. After preflight each item resolves the latest Working Manifest and revalidates its frozen inputs. It starts the Task directly, with no Task condition or verifier. Incompatibility records failure; a normally returned JSON-compatible result records success. Ordinary task failure does not block later independent items. Cancellation, input-release failure, persistence failure, or inability to continue scheduling interrupts the Plan. It introduces no task-level retry, dependency graph, result mapping, business-success predicate, or state transfer.

Every target is a string literal. The formal Component orchestration matrix permits Task Workflow to call Subworkflow or Step and permits Subworkflow to call only Step; Step calls no formal Component. Trusted Action access is governed separately by the fixed execution-role matrix above. Task Workflow nesting and calls into Task Workflow are invalid. Subworkflow-to-Subworkflow calls are also invalid in the first version; no current task demonstrates a need for that extra composition layer. Before each Working Manifest atomic update, the executor parses formal calls from the complete resulting candidate Manifest and checks every target and role. Every `ctx.call()` anywhere in a Task Workflow or Subworkflow file belongs to that file's single Component, even inside private or apparently unreachable code. Any such call in Step, Step `condition`, or Recovery Rule source is invalid. The loader performs no reachability, branch, or private-helper caller analysis. Any error rejects the entire switch and leaves the old Working Manifest active. Dynamic targets are invalid, and the executor does not rewrite source to make invalid calls legal; a revision changes the Component ID. Runtime checks only resolution and roles again and records the call; it maintains no active-Subworkflow stack. Private-function recursion remains ordinary Python implementation detail. Role decorators only mark the source function's role and create no registry, execution state, Trace, or recovery behavior. Later executor-owned wrappers use `functools.wraps`; only the logical name and Component ID establish formal identity. These structural checks improve clarity and traceability and do not form a security sandbox for arbitrary Python.

`condition(ctx, *, ...) -> bool` is optional and read-only only for Step, with inputs matching execute. A false, uncertain, or exceptional condition prevents Step entry and reaches that whole Step recovery boundary; it does not create a nested condition recovery mechanism. The condition obtains observations explicitly. Its predicate recognizes the Step responsibility range, including expected transition and already-completed states. Absent condition permits an attempt. Workflow prerequisites and final result checks belong in Steps rather than Task/Subworkflow callbacks.

Plain `@step` marks only an independently observable execution boundary. Its wrapper records identity, bound arguments, condition result, timing, Trusted Actions, observations, verification evidence, normalized return, and interruption. A Step need not be reversible or strictly idempotent, but a fresh invocation must use current observation and original arguments to continue safely from an actionable, expected transitional, or completed state. It confirms important effects before resending input, waits through transitions, returns directly when completion is already verifiable, and raises `ExecutionFailure` for an unknown or observably stalled state. A Step that cannot determine prior effects or reconstruct a compatible return is divided more narrowly. The first version adds no timeout, retry, or other policy parameters to the decorator and no formal State, Transition, generic progress, or heartbeat system; loops, observation, and result verification remain ordinary Python.

Normal values remain in Python control flow. Shared invocation handling records and propagates every error, while one Step recovery procedure owns all automatic game recovery. A Step condition or execute failure is caught before caller frames unwind. An error in Task or Subworkflow execute outside a Step is reported without replaying the Workflow or reconstructing lost frames. Only an exhausted Step recovery with paused callers may start an Agent Session or a Manifest trial. Safe Task Termination is an explicit executor action recorded only when performed, never an automatic consequence of a failure-code string.

Loading a selected complete Manifest verifies the exact source bytes of all referenced Components before use. Formal execution loads those verified bytes from `components/<sha256>.py`; source locations in `__file__`, compiled code, and tracebacks refer to that immutable stored file. Developer Candidate validation may import editable candidate source, but candidate-loaded module instances cannot populate or satisfy the formal runtime cache. Successfully loaded formal modules are reused by immutable Component ID. A legal runtime Manifest switch applies the same source verification and loading rules; an ordinary component call does not reread or rehash the file. Hash verification and compilation use the same captured bytes.

No execution layer imposes elapsed-time failure cutoffs, including low-level Trusted Actions, native focus and input setup, model requests, and external processes. The shared Trusted Action dispatcher times every invocation and records input, actual return or interruption/failure, and elapsed duration in Trace; this timer never interrupts execution. User cancellation and real operation failures remain supported. This replaces earlier leaf-timeout requirements.

Formal Components use ordinary Python returns for Normal Outcome and `ExecutionFailure` for non-user execution failures. Returned values must make distinct numeric values and their meanings explicit through descriptive fields or dictionary keys rather than ambiguous positional tuples. There is no rule based on the number of values, mandatory frozen dataclass, shared result-class Component, or cross-module class-identity contract. JSON-compatible dictionaries satisfy the semantic requirement with the current runtime. A replacement preserves the caller's required names, value types, and meanings and passes normal result validation; the executor does not infer business meaning from a Python class. Task Workflow root results remain directly JSON-compatible. Authors should express business verification as ordinary Steps; an Agent success claim cannot bypass those Steps or fabricate their results.

Public Recovery Rules are checked only after a Step invocation fails, not continuously or after success. The wrapper keeps its caller frames paused, enumerates detect in stable logical-name order, and obtains observations only as requested by implementations. A detect error stops enumeration and records the original error. Multiple matches, recover errors, or a non-None recover return end this deterministic attempt without another rule or immediate Step invocation. Otherwise it runs the unique matching recover when present, resolves the current Step through the latest Manifest, and invokes it once with saved original arguments. Compatible return resumes callers; repeated failure or incompatible return reaches Agent/Manifest handling or explicit termination. User controls and failures that prevent safe recording or input release bypass game recovery. Rule errors use the same invocation logging but never recursively recover themselves.

A replacement Step reconnects to the paused caller only through a new invocation after atomic Working Manifest selection and verification of its source against its Component ID, stable logical name, and `@step` role. It preserves every original parameter name, annotation, required status, and default, but may add keyword-only parameters with JSON-compatible defaults. It also preserves return category and meaning, including caller-required named values, types, and meanings, accepts a fresh copy of the wrapper's saved arguments, and satisfies its current `condition` and safe-continuation contract. Any need for a new required argument, changed upstream control flow, incompatible result, or lost ability to classify current effects prevents reconnection. The new Component may serve later valid calls, but changed Workflow source cannot replace a paused caller frame. No interface-version or compatibility-level model is introduced.

Subworkflows compose Steps through the ordinary Python stack and are not recovery boundaries. A nested Step interruption retains every caller frame and successful recovery returns through that chain. Task/Subworkflow execute errors outside a Step are reported without replay or hot-patching. Changed Workflow implementations apply only to later ordinary calls; entered frames retain their implementation and locals. The first version does not restore frames after a crash; Checkpoint/Resume remains deferred.

Checkpoint/Resume remains deferred. If it is added later, a Task Workflow explicitly saves verifiable ordinary data, and a newer implementation receives that data together with the previous Component ID for migration; it never receives an old Workflow object, frame, locals, or call stack. The first version rejects general state export, inheritance, migration, the former Step-graph Recovery Entry, arbitrary Task Workflow recovery entrypoints, and reconstruction or hot-patching of Python frames.

The first version does not automatically promote a first occurrence into a public Recovery Rule. The exact local-to-public maintenance sequence is deferred to Stage 3.5 under ADR 0025; every executable change must remain a formal candidate Component with real trial evidence and separate human approval.

## Shared invocation, recovery, and outer error boundaries

One internal invocation helper covers Step condition, Component execute, Trusted Actions, and Recovery Rule entrypoints. It owns frame entry/exit, timing, matching Trace events, result validation, and original exception recording. User controls remain distinct. Sharing the helper grants no extra permission. There is no Task condition or verifier invocation path.

Recovery remains outside the invocation helper and exists only at the whole Step boundary. There is one rule-evaluation and Step-reinvocation procedure; no phase registry, new exception hierarchy, or separate condition/verification retry system is added. Business verification is an ordinary Step responsibility.

The application worker wraps execution, Ledger completion, input-session cleanup, and final public-result publication. Unhandled worker or cleanup errors preserve the previous result and original diagnostics, publish a terminal fatal result, and prevent further starts. Failure to record or release input stops work instead of invoking game recovery. No Run may remain marked running just because cleanup raised.

The interaction layer catches operation errors, logs original diagnostics, and displays a copyable error dialog. Completed failed execution results also reach that interaction reporting path. Main-thread, GUI callback, and otherwise unhandled worker-thread exceptions have an outer fatal boundary: log full original diagnostics, show a large bilingual Chinese/English explanation that the application cannot continue and the error can be reported, with visible selectable traceback and an explicit copy action, then exit unsuccessfully. CLI uses the same original-error logging and prints fatal wording and diagnostics to stderr without starting a GUI. Fatal errors are not task recovery. GUI presentation must occur on the GUI thread. Tests distinguish ordinary handled errors from fatal exits and verify errors from execution, recovery, cleanup, and interaction.
