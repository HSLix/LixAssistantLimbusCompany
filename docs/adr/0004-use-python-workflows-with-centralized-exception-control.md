# Use Python Workflows with Centralized Exception Control

Lix Assistant models Task Workflows, Subworkflows, and independently recoverable Steps as immutable Python Components. Python supplies control flow, local variables, returns, and the call stack; this replaces the explicit YAML Step graph and avoids maintaining a growing custom Workflow language and interpreter. Each formal Component uses a typed `execute(ctx, *, ...)` signature as its sole input contract. Task Workflow and Step may expose a matching trusted `condition(ctx, *, ...)`, while Subworkflow exposes only `execute`; Trusted Actions provide low-level screenshot, recognition, input, and wait operations. Input annotations recursively support JSON scalars, `Literal`, optional values, `list[T]`, and `dict[str, T]`, with JSON-compatible defaults; arbitrary classes, Pydantic models, Enum types, sets, tuples, and non-optional unions are excluded. This supports UI and Agent inspection without an independent input schema or `ctx.inputs`. A module docstring is the sole natural-language Component description and is read by parsing source; there is no independent `description` field. Temporary Action Plans remain `execute(ctx)` and receive state through their JSON Context snapshot.

Exactly one parameterless `@task_workflow`, `@sub_workflow`, or `@step` on each Workflow or Step entrypoint is the sole source of its `ctx.call()` role. After source-hash verification, the loader parses that decorator and binds the stable logical name from the Manifest. These entries do not repeat `component_kind`, and paths, filenames, logical-name prefixes, and tags never infer role. Recovery Rules do not add a fourth decorator: they are immutable Components registered in a dedicated `recovery_rules` mapping with fixed `detect(ctx) -> bool` and `recover(ctx) -> None` entrypoints and are invoked only by the executor. Task and Sub Workflow wrappers write the same Ledger record shape with `workflow_kind = task | sub` and final `success | failure`: Subworkflow normal return is success and any non-normal exit is failure, without a verifier. Safe Task Termination is performed and counted only on the owning Task record rather than duplicated on active Subworkflows. Nested Subworkflows use ordinary Python calls and their wrappers add no recovery mechanism.

One terminal cause propagates the same executor-owned `failure_code` to every active Workflow record unwound by it. Ancestors are not translated to generic child-failure codes; their messages, parent-call identities, and Trace links retain the actual source, while already returned Subworkflows remain successful.

One Agent invocation is one Trace event and is attributed to the owning Task Workflow plus every active ancestor Subworkflow whose call span contains it. Those successful spans are Agent-assisted; already returned and sibling Subworkflows are unaffected. Per-Workflow counts are intentionally overlapping health observations, so application-wide Agent totals use unique Trace events rather than sums across nested Ledger records.

Public Recovery Rule attempts and results and Step reinvocations use the same span attribution. Deterministic recovery alone does not change a successful span from strict to Agent-assisted. These per-Workflow recovery counts measure Component reliance and intentionally overlap; application-wide totals again come from unique Trace events rather than nested Ledger sums.

Each Task Workflow, Subworkflow, or Step occupies exactly one Python source file containing one decorated `execute` entrypoint. Task Workflow and Step may also contain their optional `condition`, Task Workflow contains its required `verify`, and Subworkflow cannot define either callable. Source-local result classes and ordinary implementation functions belong to that Component. Multiple formal Components never share a file, keeping Agent retrieval, hashing, validation, and replacement independently scoped; paths and filenames still carry no role or logical-name authority.

Formal Task Workflow, Subworkflow, Step, condition, verifier, Recovery Rule, every private function in those source files, and every Temporary Action Plan contain no `except`. Loaders reject every exception-handler AST node without analyzing its type, reachability, or re-raise behavior. `try/finally` remains legal for cleanup, but `return`, `break`, `continue`, and `raise` are forbidden throughout every `finally` suite without reachability or bare-rethrow analysis. Legal cleanup lets the original exception propagate naturally; a cleanup failure preserves the full Python exception chain for Trace. All formal exceptions therefore reach the applicable wrapper and Trace, while Temporary Action Plan exceptions reach its Adapter. Step exceptions normalize into `ExecutionInterruption` and the existing recovery ladder; Step-external exceptions directly produce Execution Anomaly, while verifier exceptions record terminal Task failure without Agent rescue. A legitimately ignorable condition is an explicit ordinary result handled by normal branching, not a swallowed exception. A failed plan's alternative is a new immutable plan identity. Trusted Action implementations alone may catch low-level exceptions, and must record the original before returning a documented explicit result or re-raising a normalized exception; they may not silently pass or fabricate success.

User cancellation is an executor control signal, not an exception. Wrappers and Trusted Actions stop new input; cancellation bypasses recovery and Agent, cannot be caught or cleared by source, and interrupts a containing Automation Plan without later items. If a Task run record already exists, it records `failure_code: user_cancelled`; otherwise no Task result is created. `safe_termination_performed` reflects only an action the executor actually completed and is not inferred from whether cancellation occurred during resolution, input validation, condition, or execution. Exact position remains in Trace. A process crash instead uses `process_crash` when a Task record exists and cannot claim completed safe termination.

Workflow and Step Components call one another only through `ctx.call(logical_name, **arguments)`. Each call resolves the current Working Manifest, verifies identity, hash, role, and arguments, invokes the corresponding wrapper, and records the actual resolution. Candidate loading checks statically visible targets; unresolved runtime targets raise `ExecutionInterruption`. Direct imports of Workflow or Step implementations and separate Component Ref, cache, binding, or invalidation mechanisms are rejected. Ordinary functions inside Component source and standard-library calls remain unmodeled Python implementation details. Trusted Actions are imported from the shipped Runtime API and called as ordinary functions, without a `ctx.action()` API. Their dedicated Manifest mapping pins immutable approved implementations and classifies each once as `observe` or `control`. The executor hard-codes access by execution role: Task Workflow and Subworkflow `execute`, Task Workflow and Step `condition`, and Recovery Rule `detect` use `observe`; Step `execute`, Recovery Rule `recover`, and Temporary Action Plan use both; Task Workflow `verify` uses none. `wait` is `control` so Workflow code cannot bypass Step timing and recovery. Candidate loading rejects direct, statically visible violations in formal entrypoints but does not build or propagate permissions through a private-function call graph. Trusted Action wrappers are the authoritative boundary: they recheck classification and the actual execution role before acting, reject indirect violations, and trace every invocation. No component list, user-defined permission, allow/deny rule, permission object, helper permission, or inheritance exists. The Agent cannot create or replace a Trusted Action during a Top-level Execution.

A runtime Trusted Action access violation is an execution-contract error rather than an environmental interruption. The wrapper rejects it before the action, produces an Execution Anomaly directly, and bypasses public Deterministic Recovery. Agent repair may rescue the current task only when a Step wrapper remains paused and a fresh Step implementation satisfies the existing reconnection contract. Outside a Step, corrected Workflow or Subworkflow code applies only to later calls because the failed frame cannot be safely continued. A verifier violation is terminal for the current task. A violation inside Recovery Rule detection or recovery leaves the Step paused, so the Agent may repair the scene or prepare a candidate rule before the executor retries that Step. No case reconstructs an unwound frame, hot-patches a Workflow frame, or replaces the verifier bound at task start.

Asset access is confined to the Trusted Actions that consume it. Formal and temporary Python pass a stable semantic name such as `ui/popup/confirm`, never a language, extension, or path. The Trusted Action uses `ctx.game_language` and the current Working Manifest's Asset mapping to verify and match a shared-library file, with deterministic cross-language fallback when the current language is absent. Assets are content-hashed shared files rather than Components and have no Component IDs or `ctx.asset()` interface.

Run Context is an executor-owned runtime interface, not a business-data store. It exposes component invocation, Target Window and language access, Working Manifest resolution, Trace, evidence, cancellation, and overall budgets; only the executor, wrappers, and Trusted Actions manage its internal state. Formal Components have no arbitrary mutable Context fields, shared task dictionary, or generic update API: inputs, loop values, intermediate business results, and outputs use named parameters, ordinary returns, and local variables. `ctx.call()` normalizes inputs and supplies independent copies; startup and Step-boundary snapshots remain immutable for verification and fresh invocation. A Subworkflow returns any scheduling suggestion for its Task Workflow caller to apply. External game state is re-observed rather than inferred from memory, and Agent Python receives only a JSON snapshot assembled from explicit values and runtime records, never the live Context. No child Context or merge mechanism is introduced.

Repeated goals remain ordinary Task Workflow loops over a Subworkflow that completes one iteration. Each normal Subworkflow return updates Task Workflow local completion data, and the Task Workflow eventually returns a value matching an explicit, directly JSON-compatible return annotation. Root results cannot use tuples or source-local named results. The task-start-bound `verify(ctx, result, *, ...)` uses an exactly matching result annotation and compares only the validated result with immutable original inputs; it does not read Trace, observe the game, call formal Components, or maintain counters. Only the exact boolean `True` records `success`. An invalid or non-normalizable root result, false verification, or verifier exception is terminal for that Task Workflow: its call stack has ended, so the executor records `failure` with a stable `failure_code` and user-facing `failure_message`, without Agent rescue or retry. Only the executor selects the code from ordinary internal constants; Component and Agent output provide facts but cannot choose or override it. Published meanings only extend, never change or get reused, and an unclassified failure uses `execution_failed` while full detail remains in Trace. Failure position and process remain in Trace rather than a duplicated `failure_stage`. Trace remains factual diagnostic, recovery, Agent, and audit evidence rather than a normal business-data channel. The executor creates no progress event or fabricated return. A paused Step wrapper preserves the live Python loop frame during recovery, but the first version does not persist or reconstruct frames and loop positions after a process crash; it terminates safely or restarts from an observable known point, leaving Checkpoints deferred.

Automation Plan is user-saved configuration rather than a Component or Manifest entry. It contains only an ordered list of Task Workflow stable logical names and explicit input dictionaries; repeated logical names form separate calls and list position is sufficient identity. Before any task starts, the executor parses the complete structure, resolves every name to a Task Workflow through the initial Working Manifest, and binds, type-checks, and normalizes every input. It reports all preflight errors together; any error records `status: interrupted` with `reason: invalid_plan`, invokes no task or condition, creates no Task Workflow result, and contributes to no Workflow success statistics. Preflight does not evaluate task conditions, environmental eligibility, dependencies, predicted success, or adjacency compatibility. The running Plan then retains only that frozen ordered list and its current index, not an execution stack. Before each item it resolves the latest Working Manifest again, validates the frozen input against the current Task Workflow, and evaluates its current condition. Each considered item records only `success` or `failure`; failed conditions and post-preflight Working Manifest incompatibility remain failures even when `execute()` is not entered, without Agent repair or rollback. A compatibility failure is attributed to Workflow statistics only when an actual Task Workflow Component ID still resolves. Safe Task Termination is a separate executor action recorded alongside `failure`, not another result category. Results never block later items. After traversing all items, the Plan records `completed` and an ordered summary of task logical name, normalized input, result, duration, and Run ID regardless of individual outcomes. Cancellation, process failure, or inability to continue scheduling records `interrupted`. Automation Plan has no item-level condition, retry, dependency, failure policy, result mapping, verifier, aggregate business-success predicate, success rate, Agent recovery path, or operating-policy branch. A direct Task Workflow run has no next item and ends after recording its result.

Every target is a string literal. The formal Component orchestration matrix permits Task Workflow to call Subworkflow or Step and permits Subworkflow to call Subworkflow or Step; Step calls no formal Component. Trusted Action access is governed separately by the fixed execution-role matrix above. Task Workflow nesting and calls into Task Workflow are invalid. Before each Working Manifest atomic update, the executor parses formal calls from the complete resulting candidate Manifest, checks every target and role, builds the directed Subworkflow graph, and rejects direct or indirect cycles with the complete cycle path. Every `ctx.call()` anywhere in a Task Workflow or Subworkflow file belongs to that file's single Component, even inside private or apparently unreachable code. Any such call in Step, `condition`, `verify`, or Recovery Rule source is invalid. The loader performs no reachability, branch, or private-helper caller analysis. Any error rejects the entire switch and leaves the old Working Manifest active. Dynamic targets are invalid, and the executor does not rewrite source to remove cycles; a revision creates a new hash and Component ID. Runtime checks only resolution and roles again and records the call; it maintains no active-Subworkflow stack, recursion guard, or nesting-depth limit. Private-function recursion remains ordinary Python implementation detail. All role decorators use `functools.wraps`, but only logical name, Component ID, and content hash establish formal identity. These structural checks improve clarity and traceability and do not form a security sandbox for arbitrary Python.

`condition` remains optional and read-only only for Task Workflow and Step. A normal false Task condition records `failure_code: task_condition_not_satisfied` without Agent; an exception produces Execution Anomaly and may let Agent repair only later capability, while the current non-retried item records `task_condition_check_failed`. Neither enters `execute()` or performs Safe Task Termination. Task condition only grants launch permission and never restores the environment; a recoverable prerequisite belongs in the first Step. Step condition checks before its first and every recovery-controlled fresh invocation. False, uncertainty, or exception produces `ExecutionInterruption` inside its wrapper and never becomes a Workflow branch value; public recovery and a fresh observation precede another condition check, and only satisfaction permits Step invocation before repeated failure escalates. Its predicate accepts the entire observable responsibility range, including expected transition and already-completed states, rather than requiring one instantaneous action target. Subworkflow defines only `execute`; its required environment recognition and entry protection belong to its first relevant Step. Conditions use trusted observation and recognition without changing external state. Absence permits an attempt from any state. There is no Subworkflow entry recovery or safe-reentry contract, Condition Expression, expression tree, or condition DSL.

Plain `@step` marks only an independently observable execution boundary. Its wrapper records identity, bound arguments, condition result, timing, Trusted Actions, observations, verification evidence, normalized return, and interruption. A Step need not be reversible or strictly idempotent, but a fresh invocation must use current observation and original arguments to continue safely from an actionable, expected transitional, or completed state. It confirms important effects before resending input, waits through transitions, returns directly when completion is already verifiable, and raises `ExecutionInterruption` after its own reasonable deadline for an unknown or stalled state. A Step that cannot determine prior effects or reconstruct a compatible return is divided more narrowly. The first version adds no timeout, retry, or other policy parameters to the decorator and no formal State, Transition, generic progress, or heartbeat system; loops, observation, deadlines, and result verification remain ordinary Python.

Normal values remain in Python control flow. An `ExecutionInterruption` inside a Step is caught by `@step` before its caller frame unwinds and enters executor-owned recovery; an interruption outside a Step produces an Execution Anomaly directly. Only the executor owns Trace, Deterministic Recovery, Agent invocation, and Safe Task Termination. Task Workflows remain user-startable roots, Subworkflows remain reusable acyclic local flows over Steps and other Subworkflows, and Automation Plan composes complete Task Workflows.

Formal Python loads through standard module loading from Manifest-fixed paths and hashes. Agent Python is instead saved as immutable source and loaded only inside a runner subprocess from a JSON Context snapshot.

Formal Components use normal Python returns for Normal Outcome and raise `ExecutionInterruption` for the interruption channel. Step and Subworkflow single values remain JSON compatible; only their unambiguous two-item results may use positional tuples, while three or more fixed values use a source-local frozen named result whose fields normalize to JSON. Named results are structural: callers use field access and cannot import or inspect the source-local class, while class name, module, and Python identity are outside the contract. `ctx.call()` returns the actual instance and Trace stores normalized fields; compatible replacements preserve field names, annotations, and meanings rather than class identity. Dynamic mappings remain dictionaries, Temporary Action Plans return only JSON-compatible values, and there is no shared result Component, `Outcome` type, or result schema. Every Task Workflow instead declares and returns a directly JSON-compatible root result and requires `verify(ctx, result, *, ...) -> bool` with the same result annotation; its exact identity, hash, and original inputs bind at task start. Only after a normal root return passes annotation validation and normalization does the executor invoke this verifier, and only the exact boolean `True` marks success. A completed Agent plan must first restore the current Step and ordinary return chain; it cannot trigger early verification, fabricate task data, or unwind past remaining Workflow actions. A parent-side Temporary Plan Adapter hides JSON transport, validation, Trace, timeouts, and exception conversion so Temporary Action Plans themselves return only ordinary JSON-compatible values.

Public Recovery Rules are checked only inside an `@step` wrapper after that Step raises `ExecutionInterruption`; they are not continuously polled or applied to interruptions outside Steps. The wrapper keeps its caller frame paused and evaluates detections against one fresh observation in stable logical-name order, without a Manifest ordering field. If any `detect(ctx)` raises, enumeration stops immediately: Trace records the rule and original exception, no detection is treated as a non-match, no `recover(ctx)` runs, and later rules are not checked. This directly produces an Execution Anomaly while the Step remains paused for Agent handling or Safe Task Termination. Otherwise the wrapper runs one uniquely matching `recover(ctx)` when available. If that call raises or returns anything other than `None`, the executor records a Recovery Rule execution-contract failure and directly produces an Execution Anomaly: it tries no other rule and does not immediately invoke the current Step because recovery may have partially changed the environment. The Step remains paused for Agent re-observation and planning or Safe Task Termination. A normally completed recovery lets the executor resolve the current Step through the latest Working Manifest and invoke it once with the original arguments. A compatible return resumes the still-present caller; another interruption, failed condition, or incompatible return escalates to the Agent. After an Agent plan, the executor may resolve and invoke the Step again when still applicable.

A replacement Step reconnects to the paused caller only through a new invocation after atomic Working Manifest selection and verification of its source, identity, hash, stable logical name, and `@step` role. It preserves every original parameter name, annotation, required status, and default, but may add keyword-only parameters with JSON-compatible defaults. It also preserves return category and meaning, including tuple positions or named-result fields and annotations, accepts a fresh copy of the wrapper's saved arguments, and satisfies its current `condition` and safe-continuation contract. Any need for a new required argument, changed upstream control flow, incompatible result, or lost ability to classify current effects prevents reconnection. The new Component may serve later valid calls, but changed Workflow source cannot replace a paused caller frame. No interface-version or compatibility-level model is introduced.

Subworkflows compose Steps and other acyclic Subworkflows and record calls and Ledger data. They use only the ordinary Python call stack, are not restarted, and are not recovery boundaries. A nested Step interruption leaves every caller frame paused in place; successful recovery returns through that chain naturally rather than rebuilding it. Task Workflows remain thin roots that own top-level inputs, ordinary business order, loops, branches, local result aggregation, JSON-compatible root results, and their final verifier; recognition and environmental operations move down when useful without turning every small Python decision into a Component. An interruption outside a Step directly produces an Execution Anomaly. This design restores no unwound frame: the Step wrapper prevents caller unwinding in the first place. A replacement Task Workflow never receives the active frame's locals, loop position, or remaining control flow and serves only later fresh calls. General state export, inheritance, migration, Checkpoint/Resume, the former Step-graph Recovery Entry, Workflow restart behavior, arbitrary Task Workflow recovery entrypoints, and reconstruction or hot-patching of Python frames are rejected from the first version.

An unknown exception's first successful Agent plan is always incorporated into a candidate version of that Workflow as an ordinary local Python handling branch, never directly as a public Recovery Rule. The branch is not a new Component or recovery mechanism; it uses deterministic recognition, actions, and verification and raises `ExecutionInterruption` on failure. Only successful reuse at a compatible real occurrence in another Workflow permits extraction into a public rule. Extraction atomically adds the rule and rebuilds the original candidate Workflow without the duplicated branch; the second Workflow changes only if its source must be corrected to expose the failure through the formal execution contract. This fixed evolution order avoids asking the Agent to classify global scope from one occurrence.
