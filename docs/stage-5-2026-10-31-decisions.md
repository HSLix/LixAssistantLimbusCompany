# Stage 5 — 工作台与 Session 设计修订

本轮 #336 补充决定见[实施前记录](stage-5-336-decisions.md)：首条用户消息提交前可调整模式 / 来源，首次提交时固定两者；Developer GUI 的 Manifest 选择及人工运行入口删除，Agent 试运行完整保留。下文折叠选择区与右上布局是已被替代的历史决定。

状态：2026-10-31 逐项 grill 已确认，开发者以“开始 review”授权进入影响审查与正式文档统一。本记录保留决定来源；当前契约集中在 [Stage 5 规格](stage-5-agent-workbench.md)及 [ADR 0034](adr/0034-extend-developer-agent-with-reviewed-page-drafts.md)。开发者已确认合并原第 2 / 3 票并批准其余拆分，六票已发布为 #335–#340；不表示产品实现完成。

## 已明确的变更

- 取消 Repair / Workbench 两个独立页面，合并为一个“Agent 工作台”页面。本决定替代 ADR 0034 的双入口设计及本轮早先的“双入口共享 Candidate、分别聊天”决定。
- 删除 Developer GUI 各页上方共用的 Manifest 选择、刷新与试运行区域，将 Developer Selected Manifest 选择及所选 Plan 试运行放入工作台右上角可展开 / 收起的区域。每次打开 Manifest 选择列表前自动刷新，不另设刷新按钮。选择仍不修改 Default 或 Candidate 来源。
- 工作台布局参考开发者提供的第二张图：历史会话侧栏、聊天主体、底部输入区；New Conversation 使用小按钮，不采用示意图中占据大面积的圆形入口。右上角展开区域参考第三张图，但以本轮明确要求的选择前自动刷新替代图中的独立刷新按钮。图片仅提供布局参考，不自动引入图片文字所暗示的行为契约。
- 每个 Session 维护各自 Candidate，替代 Agent 全局共享 Candidate。项目根目录现有 Candidate 仅供开发者使用，不能被 GUI Agent 隐式接管、迁移或清空。
- Construct / Repair 保留为同一工作台内的两种模式；首条用户消息提交前可调整模式和来源，首次提交时两者固定。每种模式有自己的工具白名单和初始 Prompt；工具声明与宿主分发均按该 Session 模式执行白名单，不能只靠 Prompt 限权，也不能因共用页面而合并权限。历史 Session 的模式不可通过界面模式切换被隐式改变。
- 一个 Session 对应一段连续对话；聊天、Candidate、固定 Diff 基线和模式一起持久保留。切换会话或重启应用后可恢复并继续，新建 Session 不清空旧 Session。历史日志不能单独冒充可恢复 Session；旧数据原样保留，不自动迁移。
- 新建 Construct Session 可选择空白草稿（含最小 Python Plan），或选择已发布 Manifest 作为扩展基线；Repair Session 必须选择已发布 Manifest 作为修复基线。来源在首条用户消息提交时确定，开始对话后不重建草稿、不改变其来源或固定 Diff 基线；原 Developer Selected Manifest 设计已由本轮删除入口决定替代。空白初始化必须与现有隐式选用 Default 的路径明确区分。
- Session 内取消“重建 Candidate”：更换基线或从头开始必须新建 Session，旧 Session 的聊天、Candidate 与固定基线保留。该决定取代早先关于重建时重置两边对话的待讨论方案；不自动改变开发者手工 Candidate 的现有初始化命令。
- Agent 执行、等待人工答复或试运行期间禁止切换 / 新建 Session；完成或取消并收尾后恢复。当前会话的聊天显示和取消入口保持可用，不提供多个 Session 后台并行运行。答复、工具结果及试运行证据归属发起它们的会话，不能随界面选择改变。
- CLI Agent Repair 同样使用独立 Session Candidate，不再直接修改开发者手工 Candidate。手工初始化、编辑、校验和发布等开发者命令继续使用原 Candidate。历史 Session 保存在 LALC 数据目录；现有草稿与旧日志原样保留，不自动迁移为 Session。
- CLI / GUI 使用同一份 Session 存储：CLI 创建的 Repair Session 可在 GUI 历史列表打开，CLI 可按 Session ID 继续 Repair 会话；同一 Session 同时只能有一个入口执行。实际权限取模式白名单与当前入口能力的交集：GUI 中开放人工答复 / 操作请求，CLI 不开放弹窗工具，也不运行 Construct Session。不因 GUI 对话历史含有 GUI 工具记录而向 CLI 授予这些能力。
- Session 独立保存聊天、Candidate、固定 Diff 基线和页面草稿；Asset Library、已发布 Manifest、正式页面、业务配置及外部知识库仍全局共享。某 Session 新增 / 归档移除 Asset 会影响之后的匹配，安装页面会修改全局正式页面；切换 Session 不撤销这些全局变更。页面预览的试填配置仍只在内存中，不随安装导入正式配置。
- 首版不提供 Session 删除入口，也不自动清理 Session；保留历史对话、未发布草稿及交互证据。归档与清理能力留后续，不作为本阶段实施项；持续磁盘占用是本方案的已知限制。
- Developer Selected Manifest 是开发者级全局选择，切换 Session 不改变它。Publish 显示新 Manifest ID，但不自动选中新版本。每次展开列表前刷新并保留当前选择；所选版本不可用时明确报错，不自动替换为另一版本。Agent 试运行工具仍须明确指定 Manifest ID，不能把全局选择或本 Session 最新发布物当作隐式目标。
- 页面预览改为同进程的应用级模态窗口，替代此前独立进程方案，减少进程启动、通信和退出清理。预览期间锁住 LALC 其他 User / Developer 窗口；点击被锁窗口时提醒并强调 / 聚焦现有预览窗口，不另叠一层警告对话框。游戏与其他应用不被锁住。预览绑定发起 Session 和指定草稿版本，期间不能切换 / 新建 Session 或启动新的 Agent 修改；关闭后解除锁定。
- 预览配置仍为内存副本，关闭丢弃、安装不导入试填值；人工安装仍绑定实际预览版本。同进程预览不提供页面代码故障隔离，也不保证关闭后卸载页面导入的所有模块；页面卡死或崩溃可能影响主应用。正式规格中独立进程与重开必然清除模块状态的旧要求由本决定替代，具体加载方式须如实记录限制。
- 页面安装由开发者人工对照确认：预览拟安装版本（“安装后”，尚未写入正式目录），同名正式页面存在时另行运行其当前版本预览（“安装前”）。两者各自使用内存试填配置，不共享试填修改，也不把试填值写入正式配置。不存在同名正式页时仅展示拟安装版本并说明是新增。开发者检查是否符合预期后确认安装，不引入自动版本冲突检测、自动阻止覆盖或智能合并；这不取消必要的目标路径校验、预览版本绑定和安装失败保留原页等边界。
- 当前正式页面可能已被其他 Session 或开发者修改；若人工对比发现差异需要适配，可让当前 Session 的 Agent 通过受控只读入口访问最新正式页面，在自己的页面草稿中继续修改，再次预览确认。该能力不授予直接编辑正式目录的权限，也不要求重建 Session Candidate。人工确认可能覆盖其他 Session 已安装的页面改动，界面应如实区分两个预览的版本与角色。
- 安装审查采用一个同进程应用级模态对比窗口：左右分别运行“当前正式页”和“拟安装页”的独立页面实例，统一提供确认安装入口。两个页面均可交互，其他 LALC User / Developer 窗口保持锁定；无同名正式页时当前侧标明新增 / 不存在。关闭对比窗口后解除锁定。
- 应用意外退出后保留已落盘聊天、草稿与日志，未完成轮次标记为已中断。重启可查看并继续 Session，但不自动重发模型请求、重跑工具、恢复试运行或沿用未完成的人工确认；开发者再次发送消息后，Agent 检查当前文件和实际状态再继续。已完成的全局变更不自动回滚，包括新增 Asset 和已安装页面；尚未保存内容不保证恢复。
- 每轮 Agent 首次访问某个外部知识库 Git 仓库时自动尝试一次 fetch，同轮后续读取不重复自动 fetch；Agent 可显式请求 fetch。失败报告实际错误、不自动重试，本地资料仍可只读访问；每次 fetch 尝试后均返回 status。同轮远端后续更新需显式 fetch 才可取得。
- Git 更新比较默认使用当前分支配置的 upstream，记录该参考引用 fetch 前后提交及完整区间差异。无 upstream 或处于 detached HEAD 时报告未确定参考分支，不猜测 main / master，也不声称已是最新；本地文件及指定提交仍可读取。跟踪关系由开发者通过 Git 配置，首版不新增分支选择界面。未确定参考分支不构成自动选择远端或扩大 Git 工具参数权限的授权。
- Developer GUI 的 Construct / Repair 均可编辑自身 Candidate、专用新增 Component / Recovery Rule、校验、检查及受控新增 / 归档移除 Asset、Publish、指定已发布版本试运行、读取运行日志、只读检索外部知识库及调用受控 Git 工具。两种模式均开放“请求人工答复或操作并等待反馈”（此前称“同轮提问”），沿用 Skip 不授权、取消唤醒、不隐式恢复暂停等边界。页面草稿构建、预览及人工版本确认安装流程仅 Construct 模式开放。两者均无通用终端、任意文件操作或修改 Default 的权限。
- Developer GUI 的 Repair 模式与 User GUI 执行期间的 Runtime Repair 必须分开。后者在 Stage 6 实现：有人监督 / 值守时才开放人工答复或操作请求，无人值守时不开放；不能因复用开发工具而默认继承。值守状态来源、变化时机和等待中转为无人值守的处理留 Stage 6 明确，不加入 Stage 5 实施范围。Runtime 不提供删除工具及对应权限的既有约束保持。
